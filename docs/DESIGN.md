## 0. 一句话定位

**一套面向 agent 的 MCP 服务**:把长知识类视频(30 分钟级)加工成"可看、可校、可总结"的材料——**差帧图 + 带时间戳转录 + 预筛选截图**——供 agent 调用工具完成**校准、总结、报告生成**;用户**通过与 agent 对话**把关、纠偏、二次修改。

### 0.1 三条铁律(本设计的基本假设)

1. **识别与判断归 agent,不归工具。** 图文匹配、转录纠错、交叉印证、总结——这些"需要看图/读懂语义"的事,**全部由 agent 自己的多模态能力完成**。工具只提供材料、执行确定性动作、保存 agent 给出的结论。
2. **工具不接触任何模型 API、不持有任何密钥。** 因为识别由 agent 做,工具内**不存在**任何"调用视觉/语言模型"的代码路径,自然也没有 key 泄露面。
3. **MCP 是通用协议,不绑定具体 agent。** 凡支持 MCP 的 agent 都应能接入;本设计不为某个特定 agent 定制,只依赖两点通用能力:**能看图(多模态)**、**能调工具**。

> 推论:本工具**要求接入的 agent 具备多模态能力**。若 agent 不能看图,步 2/3 无法进行(步 1 仍可用)。

## 1. 背景与要解决的问题

### 1.1 问题

长知识类视频直接交给多模态大模型总结,有两组矛盾:

1. **成本/上下文矛盾**:整段视频 token 量大(30 分钟约 50 万 token),而绝大部分画面是静止重复信息。
2. **信息漏失矛盾**:均匀采样(1fps)会漏掉持续 <1s 的关键画面(PPT 翻页、板书切换、演示中的标注);只靠语音转录又丢掉画面独有信息(图表、数值区间、标注线、形态)。

### 1.2 核心思路

> **算法先粗筛"哪里值得看",agent 再看这些地方,人通过对话把关。**

实测依据(RESEARCH.md 第 5 节):知识类视频的**画面切换点 ≈ 内容切换点**。教学视频里每个案例切换都对应差帧图上的一个峰,且与语音时间戳几乎一一吻合。

## 2. 设计原则

| 原则 | 说明 |
|------|------|
| **识别归 agent** | 工具**不做任何模型推理**。所有"看图/理解/判断"由 agent 完成;工具负责给材料(图、文、曲线)、干算法活(差帧、抽帧、扫描)、存结论(把 agent 的判断落盘)。 |
| **工具零密钥** | 工具内不存在调用外部模型 API 的路径,不读取任何 API key。 |
| **面向 agent、协议通用** | 交付物是标准 MCP 服务;不为特定 agent 定制,只假设"能看图 + 能调工具"。 |
| **原子步 + 可迭代** | 步 1 一次调用做完(无中间态);步 2 天生迭代(agent 反复调工具);步 3/4 单次产出但允许凭新提示重做。 |
| **一切以时间轴对齐** | 差帧图、截图、转录、校准结论挂在同一条时间轴上,视图按轴联动,**并可回跳视频播放**。 |
| **材料即接口** | 步与步之间只通过**项目目录里的文件**通信,不靠内存状态。任何一步可单独重跑,agent 与人可直接读。 |
| **本地优先** | 计算与文件全本地;工具本身不需要外网。 |

## 3. 总体架构

### 3.1 三层角色

```
┌──────────┐   对话(自然语言)   ┌─────────────────┐   MCP 工具调用   ┌──────────────────┐
│   用户    │ ◄────────────────► │      agent       │ ◄──────────────► │  vidbrief         │
│          │   看视图/下指令      │ (自带多模态能力)  │  (stdio/HTTP)    │  MCP 服务         │
└──────────┘                    └────────┬────────┘                  └────────┬─────────┘
      ▲                                  │                                     │
      │                                  │ 看图/判断(agent 内部完成,           │ 本地计算
      │                                  │  工具不参与、不持密钥)               │
      │                                  ▼                                     ▼
      │                        ┌─────────────────┐                  ┌──────────────────┐
      └───── 打开 HTML 视图 ───│  agent 多模态推理 │                  │ 项目目录(文件)   │
              (含视频回跳)      └─────────────────┘                  └──────────────────┘
```

- **agent** 是编排者兼识别者:读用户指令 → 调 MCP 工具取材料 → **自己看图/读文并判断** → 调工具把结论存回 → 呈现结果/视图给人。
- **MCP 服务**只做三件事:**供材料、跑算法、存结论**。
- **项目目录**是唯一事实源。
- **HTML 视图**是"图形化界面",由工具渲染,浏览器打开,**时间轴与视频播放联动**。

### 3.2 四步与工具组

```
① 前处理(原子)        ② 校准(迭代)             ③ 总结(原子+可重做)    ④ 报告(原子+可重做)
preprocess()          [供] get_shot()           [供] search_transcript()  build_report()
                      [供] get_transcript()     [供] get_change_curve()   (md | html)
  ↓ 一次做完            [存] record_shot_check()  [补] request_shot()
差帧图                 [存] apply_corrections()  [写] write_summary()
转录                   [算] find_supplement_
截图                        candidates()
                      [算] extract_shot()
```

工具不按"步"硬隔离——步 2 的工具在步 3 也能用(agent 可随时补图/查转录)。"步"是**工作流叙事**,不是权限边界。

### 3.3 控制流

| 步 | 触发者 | 中断? | 迭代? |
|----|--------|-------|-------|
| ① 前处理 | agent 调 `preprocess()`,一次做完 | 否 | 否(要改需显式重跑) |
| ② 校准 | 用户与 agent 对话,agent 反复"取材料→看图判断→存结论" | 是(对话驱动) | **是**,核心特征 |
| ③ 总结 | agent 探索材料后调 `write_summary()` | 否(相对原子) | 允许二次修改 |
| ④ 报告 | agent 调 `build_report()` | 否 | 允许二次修改 |

## 4. 核心数据模型

> **本节已定稿(M0)。** 格式的**唯一权威**是 [`docs/schema/`](./schema/) ——
> 那里有 JSON Schema、示例文件(同时是测试夹具)和全局约定。
> 本节的代码侧对应物是 `crates/vidbrief-project/`。
> 两边由 `cargo test -p vidbrief-project` 做**三方锚定**校验(示例 ↔ schema ↔ Rust 类型),
> 任何一侧漂移都会红。

### 4.1 项目目录结构(材料即接口)

```
projects/<project-name>/
├── project.json                 # 项目**身份**:它是谁、从哪来、叫什么(§4.2)
├── state.bin                    # 项目**状态**:进度/核验戳/看图结论/拍板记录(§4.10)
│                                #   —— 二进制,带格式版本与 sha256;**非明文**
├── project.lock                 # 写锁:0 字节的哨兵,"锁拿不拿得到"才是判据(§4.7)
├── source/
│   ├── video.<ext>              # 源视频:硬链接 / 软链接 / 复制(§4.8)
│   └── video.meta.json          # 时长/分辨率/帧率/编码/sha256
│
├── 01_preprocess/
│   ├── change_curve.json        # 差帧图:逐时刻变化率(§4.3)
│   ├── dense_regions.json       # 算法识别出的"变化密集区"(§4.4)
│   ├── transcript.json          # 结构化转录(原始,永不就地改写)
│   ├── transcript.srt/.txt/.vtt # whisper 原始输出(便于人工核对)
│   ├── shots.json               # 截图清单 + agent 的校准结论(§4.6)
│   ├── shots/                   # 步 1 抽出的截图
│   │   └── s001_0086.0.jpg
│   ├── run.json                 # **运行记录**:这一趟跑到哪一步了(§5.4)
│   │                            #   —— 过程投影,不是材料:没有 schema、没有内容底账
│   └── timeline.html            # 四层时间线视图(含视频回跳,§9)
│
├── 02_calibrate/
│   ├── transcript.fixed.json    # 经 agent 纠错后的转录(全量副本,§4.5)
│   ├── transcript.diff.md       # 纠错对照(原文 vs 修正)
│   ├── supplement_requests.json # 补图候选 + agent 的取舍(§4.9)
│   ├── cross_validate.md        # 图文交叉印证的矛盾点清单
│   ├── shots_extra/             # 补图产出
│   ├── timeline.html            # 校准后时间线视图(可重渲染)
│   ├── calibrate.html           # 校准对照表:图 + 转录 + 结论一屏看完(§9.3)
│   └── calibration_log.md       # 迭代轨迹
│
├── 03_summary/
│   ├── agent_log.md             # agent 探索轨迹
│   ├── notes/                   # 中间笔记
│   ├── summary.md               # 总结稿
│   └── shots_extra2/            # agent 二次补图
│
└── 04_report/
    ├── report.md
    ├── report.html
    └── assets/
```

> 所有"校准结论"**由 agent 通过工具写入**,不是工具自己算出来的。
>
> ⚠️ **但它们的家不在这些明文文件里**(v0.10 起):`transcript.fixed.json`、
> `shots.json` 的 `check`/`status`、`supplement_requests.json` 的 `status`,
> 都是**状态的投影** —— 工具写出来给人读、给视图画,判据在 `state.bin`(§4.10)。
> **判据不能是随手能写的东西。**

**路径规则**:项目内所有路径都是**项目根相对路径**,用 `/` 分隔(如 `01_preprocess/shots/s007_0479.0.jpg`)。
禁止绝对路径、盘符、反斜杠与 `..` —— 项目必须能整体搬走。Rust 侧由 `RelPath` 类型强制(构造即校验)。

**为什么没有 `shot_checks.json`**:v0.7 曾把校准结论放在 `02_calibrate/shot_checks.json`,
但截图清单本身(§4.6)已经有 `check` 字段 —— 同一件事两处落点必然不同步。
M0 定稿时**取消**该文件,以 `01_preprocess/shots.json` 为唯一权威。

### 4.2 项目身份(`project.json`)

```jsonc
{
  "schema_version": 2,           // 该项目下所有 JSON 的格式版本;不符直接报错,不做静默兼容
  "id": "demo",              // 同时是目录名;ASCII 小写/数字/-/_
  "name": "第一讲 开场",        // 人类可读名,可含中文
  "created_at": "2026-09-24T21:00:00+08:00",
  "source": {
    "path": "source/video.mp4",  // 项目内位置
    "original": "D:/videos/第一讲.mp4",  // 原始绝对路径,纯信息性,不用于访问文件
    "link": "hardlink"           // hardlink | symlink | copy(§4.8)
  },
  "glossary": null               // 术语表,默认 null(关闭)
}
```

**这里只装身份。** 进度、核验戳、看图结论、拍板记录都是**状态**,住 `state.bin`(§4.10);
`rev` 也跟着走了 —— "改过几次"是状态,不是身份。

> **为什么搬走**(v0.10,devlog [260925-30] 第 2 条):这个文件明文、谁都能改,
> 而模型手里就拿着宿主给的文件工具。M4 第五轮真 agent 实测:它把 `report.done`
> 改成 `true`、`at` 编成了**未来时刻**(当时 19:54,写的是 19:58)——
> 而那几栏正是"这一步做完了没有"的判据。**明文状态 = 门是纸糊的。**

> **时长不在这里**:`duration` 归 `source/video.meta.json` 独家所有。
> 一个数字两个落点迟早会不一致,宁可让 `list_projects` 多读一个文件。

> **旧项目(v1)**:`project.json` 里还带着 `rev`/`progress`/`review` 三个字段,
> 按新结构读会被 `deny_unknown_fields` 拒掉 —— 那正是想要的信号。
> 跑一次 `vidbrief upgrade <项目>` 把它们收进 `state.bin`、把身份改写成 v2;
> **材料一个字节都不动**(§4.10)。

#### 4.2.1 用户确认(`review`,审核门)

> 这一段现在住在 **`state.bin`** 里(§4.10),不在 `project.json` 里 —— 它是**判据**,
> 而判据不能是明文可改的。字段形状没变,下面这份 JSONC 只是把它写出来给人看。

```jsonc
"review": {
  "calibrate": {                        // null = 还没被确认过
    "approved_at": "2026-09-24T21:22:30+08:00",
    "counts": {                         // 说给人听的:待裁决 3 张
      "unchecked": 0, "needing_review": 3,
      "supplement_pending": 0, "uncertain": 2
    },
    "digests": {                        // 拍板时悬着的那批长什么样(钥匙的失效判据)
      "segments":    { "12": "3f2a91c4", "31": "8b07de15" },
      "shots":       { "s001": "c41e77aa", "s002": "0d93b6f2" },
      "supplements": {}
    },
    "note": "用户说:那 3 张我知道,先往下走"   // 带着未处理项通过时的原话
  }
}
```

**没有 `approved_by`** —— MCP 握手只给客户端名,拿不到模型名;而"让模型自报"就是让它编。
服务端能观察到的只有:**什么时候、当时什么状态、有没有带说明**。

**`approve` 不是门的开关,是一把"放行这一批"的钥匙。** 门按核验状态判(§6.1.1):
没核验的它照样拦,签字顶不掉。签字顶掉的只有**"核验过、但要用户拍板"**那一类 ——
用户说"这些我知道,就这样过",这句话记进 `note`,那一批才放行。

`digests` 就是**拍板时悬着的那批长什么样**,用来判断这把钥匙还作不作数:
之后材料又动过(比如又冒出来一条要拍板的),摘要对不上 → 钥匙失效 → 重新拦。
它算的是**材料**,不是文件:

| 算什么 | 不算什么 |
|--------|----------|
| 转录段**读起来是什么**(改过用改后的)、是不是标着存疑 | `conclusion` 的理由与说明(那是笔记,不是材料) |
| 截图留用/丢弃 + 看图结论(匹配 / 同步 / 画面读到什么 / 问题 / 把握) | `checked_at`(同样的结论重记一遍不算改) |
| 补图候选处理到哪一步 | 接受/拒绝的理由 |

`counts` 与 `digests` 都是"拍板那一刻的快照",给人回看用;判断本身在
`vidbrief-ops::review::gate_calibrate` 里现场数(§6.1.1)。

### 4.3 差帧图 `change_curve.json`(步 1 产出 ①)

**定义**:`差帧` = 相邻两帧画面差异算出的**一个数值**;把每对相邻帧的差异值沿**时间轴**排成直方图,就是"差帧图"。**这是视图顶层"像素直方图"的数据源。**

```jsonc
{
  "source": "source/video.mp4",
  "duration": 985.0,
  "fps_sampled": 1.0,
  "width": 480, "height": 270,   // 参与打分的缩小后尺寸
  "metric": "hist_l1_0.75+luma_0.25",   // 打分口径标识
  "generated_at": "...",
  "changes": [
    { "t": 0.0, "score": 0.0 },
    { "t": 1.0, "score": 0.017 }
    // 每采样帧一个点,score ∈ [0,1] = 该帧与上一帧的差异;首点(无前一帧)恒为 0
  ]
}
```

- `score` 沿用现有实现:**颜色直方图 L1 距离(0.75)+ 亮度均值差(0.25)**,归一化 `[0,1]`。
- 展示为**柱状/面积直方图**:横轴=时间,纵轴=变化率。保留未平滑原始值。
- `metric` 必须随算法一起改 —— 否则无法分辨磁盘上的旧文件是哪套口径算的。

### 4.4 密集区 `dense_regions.json`

```jsonc
{
  "generated_at": "...",
  "params": {                    // 可调输入
    "window": 8.0,               // 滑窗宽度 W(秒)
    "peak_threshold": 0.25,      // 孤立硬切换阈值
    "mass_k": 3.0,               // 密集区阈值 = max(窗口中位数 × k, floor)
    "mass_floor": 0.6,           // 绝对下限:防止静止视频整段被判为密集
    "merge_gap": 4.0,            // 间隔小于此值(秒)的密集区合并
    "static_break": 120.0        // 长静止判据(秒)
  },
  "stats": {                     // 本次运行算出的中间量
    "sampled_points": 985,
    "mass_median": 0.10,
    "mass_threshold": 0.60       // 实际生效的阈值
  },
  "regions": [
    { "id": 3, "start": 84.0, "end": 92.0, "mass": 3.41,
      "peak_t": 86.0, "peak_score": 1.0,
      "reason": "high_density" }   // high_density | isolated_peak | long_static_break
  ]
}
```

> **为什么连 `stats` 一起存**:密集区阈值必须随视频类型自适应。出问题时只有靠这两组数字
> 才能复现"当时为什么这样判",并据此调参重跑。`params` 的默认值在 M1 用真实长视频标定。

### 4.5 转录 `transcript.json` / `transcript.fixed.json`

> **v0.10 起**:`conclusion` / `checked_at` 这两栏的**判据在 `state.bin`**(§4.10);
> `transcript.fixed.json` 退回**投影** —— 它是"原文 + 当前结论"给人读的一份全文,
> 工具不再从它里面读结论(读它就是拿明文当判据)。

两个文件**共用同一 schema 与同一 Rust 类型**:

- `01_preprocess/transcript.json` —— 步 1 产出,**原始**。`conclusion` **恒为 `null`**。
- `02_calibrate/transcript.fixed.json` —— 步 2 产出,**全量副本** + 填结论。

```jsonc
{
  "source": "source/video.mp4",
  "model": "ggml-medium",
  "language": "zh",
  "duration": 985.0,
  "generated_at": "...",         // fixed 沿用此值,不因纠错而更新
  "segments": [
    { "id": 12, "start": 479.0, "end": 484.0,
      "text": "这是国内派森教程的第一小节",          // ASR 原文,永不就地改写
      "conclusion": {                                   // 四选一的结论,见下
        "outcome": "corrected",
        "text": "这是国内 Python 教程的第一小节",         // 改后的整句就在结论里面
        "type": "terminology",
        "note": "派森 → Python",
        "reason": "截图 s008 画面文字为「Python 列表」"
      },
      "checked_at": "2026-09-24T21:20:00+08:00" }       // 模型核验过这一段
  ]
}
```

#### 结论是**四选一**,不是一个可以在旁边另填的字段

| `outcome` | 含义 | 带什么 |
|-----------|------|--------|
| `corrected` | 改了 | `text`(改后的整句)+ `type` + `note` + `reason` |
| `kept` | 看过,**决定保留原句** | `note` + `reason` |
| `uncertain` | 看过但定不了,**留给用户裁决** | `note`(疑似写法)+ `reason` |
| (字段为 `null`) | 看过、没话说 | — |

**为什么要做成互斥的枚举,而不是"文本一栏 + 结论一栏"两个自由字段**:
两个字段各填各的,就能拼出"结论说要改、改后的文本栏空着"这种组合 —— 而**数数的时候没法算它**。
M4 第五轮实测的对照表表头就是这么来的:「改过 27 段、存疑未改 0 段、合计动过 40 段」,
27+0≠40,那 13 段"有结论、正文没动"一个桶都没进。
现在**改了的话新文本就在结论里**,"说要改"和"改成什么"没法各说各话。
`type` 也只剩错的性质(`homophone` / `terminology` / `number` / `other`)——
"存疑"是一种结论,不是一种错。

#### 每一段的五种状态(计数口径只有一处)

| 状态 | 怎么读 | 谁定得了 |
|------|--------|---------|
| **还没核验** | `checked_at` 为 `null` 且 `conclusion` 为 `null` | 模型(接着审) |
| **看过、没话说** | `checked_at` 非空、`conclusion` 为 `null` | — |
| **改了** | `conclusion.outcome == "corrected"` | — |
| **决定不改** | `conclusion.outcome == "kept"` | — |
| **要用户拍板** | `conclusion.outcome == "uncertain"` | 人 |

**五类互斥且穷尽,加起来等于总段数** —— 口径收在 `Transcript::stats()` 一处,
对照表、报告、视图都读它(`docs/schema/README.md` 同款说明)。写成断言钉在测试里,
免得将来又冒出一个"27+0≠40"。

**为什么要逐段记,而不是整份一个"审完了"的标记**:审核门要拦的是"**跳过了某一段**"。
整份记一个标记,跳了 300 段也看不出来 —— 那门等于没设。

`checked_at` 与 `conclusion` 分工:`conclusion` 记"**确实有话说**"(改了哪儿 / 哪儿没把握 /
决定不改),`checked_at` 记"**我看过这一段了**"。**审过、没问题的那一段,`conclusion` 是 `null`** ——
这正是它以前和"从没审过"分不开的原因。

用时间戳不用布尔,是因为顺带答了"这个结论是哪一轮审的"(视图与报告都要回答这个问题)。

> **为什么不就地改原文**:改了原文,"agent 到底动了哪里"就查不出来了,
> 用户也就无法核对纠错是否合理。原始产出永远是只读证据。

### 4.6 截图清单 `shots.json`

> **v0.10 起**:`status` / `check` / `reason` 这三栏的**判据在 `state.bin`**(§4.10);
> 文件里它们只是投影。读了图得出的结论,现在落的是状态。

```jsonc
{
  "generated_at": "...",         // 首次生成时间;后续增删改不更新
  "shots": [
    { "id": "s007", "t": 479.0,
      "file": "01_preprocess/shots/s007_0479.0.jpg",
      "origin": "dense_region",  // dense_region | isolated_peak | agent_request | manual
      "region_id": 3,            // 算法产物指向 dense_regions.json;补图为 null
      "status": "keep",          // keep | drop
      "reason": null,            // 处置理由:补图为什么补 / 纯色帧为什么被预标弃用
      "created_at": "...",
      "check": {                 // agent 通过 record_shot_check 写入;未校准为 null
        "match": true, "audio_visual_sync": true,
        "type_read": "Python 教程 第一节",       // 从画面读到的内容
        "neighbor_text": "这是国内 Python 教程的第一小节",
        "issues": [], "confidence": "high", "checked_at": "..." } }
  ]
}
```

**命名规则**:文件名 = `{id}_{t:06.1}.jpg`,如 `s007_0479.0.jpg`
(`{:06.1}` = 整数部分补零到至少 4 位;超过 9999 秒自然变宽,不截断)。

**id 永不复用**:`drop` 只改 `status` 不回收号,补图继续往后发。这样任何日志、报告、对话里
出现过的 `s007`,永远指同一时刻的同一张图。

> v0.7 的 `llm_supplement` 在 M0 定稿时并入 `agent_request` —— 补图都是 agent 判的,
> 分两个名字只会让人猜区别在哪。步 3 的二次补图靠存放目录(`shots_extra2/`)区分。

#### `check.evidence` —— 结论必须带能拿去对的东西

每一条看图结论都带一份**凭据**:一句**照抄**的转录原文,以及工具替它找出来的段号。

```jsonc
"check": {
  "match": true,
  "type_read": "深色编辑器截图:右上角函数名「Python 列表」、代码 xx9999",
  "issues": ["口播的「结构图」在画面上无法确认"],
  "confidence": "high",
  "evidence": { "segment": 166, "quote": "这是国内 Python 教程的第一小节" },
  "checked_at": "..."
}
```

**为什么**:没有凭据的时候,一条结论就只是**一句话** —— 事后除了再问模型一遍,没有
别的办法核实,而那是同一张嘴。M4 第四轮实测到了后果:11 张图里两张的 `match` 三轮
不一致,而**两种 `false` 落盘之后长得一模一样** —— 一张是「转录打了错字」的真歧义,
一张是**模型编了一张不存在的画面**再拿它去比,比出来的假错位。从文件里分不出哪个是哪个。

**工具核哪几样**(全是机械的,它没有眼睛):

| 查什么 | 怎么查 |
|--------|--------|
| 图还在不在 | 那张图的文件在磁盘上吗 |
| 文对不对得上 | 照抄的那句,在它指的那一段的**当前文本**里找得到吗 |
| 有没有凭据 | `null` = 摘要这套之前写的结论,门会说「补上」,不说它对或错 |

**段号是工具按 `quote` 自己找出来的,不是模型报的** —— 让模型报段号,它就会报错段号,
而那又是一处没法核对的自述。要找的不是"它说引了第几段",是"**它引的那句话真的在材料里**"。

**它挡不住什么,要说清**:画面上写了什么,**工具核不了**。所以它挡得住"编转录"和
"引一张不存在的图"——判词最常见的两根拐杖——但挡不住"编画面内容"。那要靠人,
或者靠**照抄画面上的文字**(那是 OCR 能核的东西,但得先要求模型照抄)。

**判词变了也算对不上**:引的那一段后来被人改过,结论就是照着旧文下的,门会拦住让它重看。

### 4.7 并发与多会话

MCP 走 **stdio 时是 1:1**——每个 agent 会话由客户端拉起**自己的** `vidbrief mcp` 进程,进程间相互独立。因此:

- **端口天然不冲突**:每个会话 = 一个 MCP 进程 = 自己的查看服务 = 各自绑 `127.0.0.1:0` 拿到的空闲端口。所谓"单例"是**进程内单例**,不是全局单例。
- **浏览器可多开**:查看服务是只读静态服务,任意多个标签页/会话同时看都没问题。

真正的并发风险不在端口,而在**同一项目被多个会话同时写入**(互相覆盖)。规则:

| 机制 | 做法 |
|------|------|
| **项目写锁** | 项目根放 `project.lock` —— **0 字节的哨兵**,里面不写任何东西。首个要改项目的会话取得**写锁**;其他会话只能**只读打开**,并被告知"该项目正被另一会话编辑"。进程崩溃时 OS 自动释放锁,所以不存在需要回收的死锁。 |
| **原子写** | 所有写文件走"临时文件 + 原子 rename",避免读到半截文件。 |
| **修订号(乐观并发)** | `project.json` 带 `rev`;写操作须带上读到的 `rev`,不匹配则返回 `stale`,agent 重读后再改。 |
| **进程内串行** | 同一 MCP 进程内对同一项目的写操作串行化(内部互斥)。 |

> 结论:多会话**同时查看**任意;**同时编辑同一项目**由写锁 + 修订号保证不互相踩。若将来提供 HTTP 传输供多客户端共享一个服务,则改为"单服务 + 按 session 路由 + 同样的写锁/修订号"。

**实现(M3,已落地)**:"谁持有锁"由**操作系统的文件锁**决定(`std::fs::File::try_lock`,Windows 落
`LockFileEx`、Unix 落 `flock`),**不由 `project.lock` 存不存在决定** ——
文件会一直留在项目里(空闲时也在),想知道有没有被占只能去**试着加锁**。

- **`project.lock` 是 0 字节的哨兵,里面不写任何东西。**
  M0 曾经给它定过格式(pid / host / session / opened_at)并配了 schema —— M3 实现时发现那是错的:
  Windows 的字节区间锁是**强制**的,锁住哪一段别人连**读**都读不了,于是"谁占着"这句话
  **恰恰在最需要它的时候读不到**。绕开它要么手写不安全的平台 FFI(锁到文件之外的一个字节),
  要么另起一个不被锁住的旁路文件(动项目目录格式),**而收益只是一句不改变任何人动作的诊断信息**
  (能锁住你的必然是活进程,而 pid 没法映射回"是哪个窗口")。
  空文件把这个问题连同它的两种解法一起消掉 —— 参考 cargo:它的锁文件同样是空哨兵。
  **代价**:拿不到锁时只能说"被另一个会话占用",说不出是哪一个。
- **放弃"探测 pid 还活着没有"**(M0 时设想的做法),因为:进程崩溃时 OS 会**自动释放**锁,
  不存在"陈旧锁把项目永久锁死";而 pid 会被复用,拿它当判据既不可靠又要分平台写探测代码。
- **不阻塞**:抢不到就立刻失败。等着等于把 agent 挂死;cargo 敢阻塞,是因为它的锁只跨一次构建。
- **按次取放**(2026-09-26 改的口径,清账三):MCP 服务在**一次写调用**里取锁,
  这次调用结束就放(引用计数到 0);重叠的两趟调用谁先走完都不放别人的那一份。
  此前是"首次取到进程结束",实测代价是:**一个 idle 会话能把项目占死**,而别人无路可走。
  改成按次之后,"两次调用之间被别人改过"这件事由
  **`rev` 乐观并发**兜住(`OpenProject::save` 写回前比对打开时的 `rev`,对不上就拒绝落盘
  并说明"重来一遍")—— 锁管"同时只有一个人在写",`rev` 管"我读到的那份还是不是当前那份",
  两件事:`preprocess` 那种"开头读、跑几分钟、最后整份写回"的活正好落在缝里。
  CLI 仍然每个命令取一次、命令结束即放(**同一个口径**)。
- **锁只保护材料与结论**(`project.json` / `shots.json` / `transcript.fixed.json` / 报告),
  **不保护派生视图**(`timeline.html`)—— 后者由材料推出来,两个会话同时渲染也不会有坏结果,
  而"另一个会话正开着项目"不该让查看也变成不可能。**只读的活完全不取锁。**
- **建项目阶段用目录本身当锁。** 那一刻项目目录还不存在,没有 `project.lock` 可以锁 ——
  于是拿 `fs::create_dir` 的**原子性**占位(已存在即失败),父目录(`projects/`)照旧
  `create_dir_all`(多项目共用的容器,谁铺都一样)。原来的写法是"先看目录存不存在,再
  `create_dir_all`" —— 典型 check-then-act,实测在 4 路并发下会**一个都不成**却把目录留下,
  用户重试只会得到"目录已存在,拒绝覆盖"。占位中途失败会把目录整个退掉,不留残骸。
- **文件系统不支持锁时放行,但说清楚。** 网络盘 / NFS / 某些 FUSE 上 `try_lock` 会报"不支持"
  (`ENOLCK` / `ENOSYS` / `ERROR_INVALID_FUNCTION`…)。这类**不当失败**:照样干活,
  但把原因一路带到用户面前 —— CLI 打 stderr,MCP 把这句话贴在**该项目第一次写操作的结果**最前面。
  > cargo 在这里是**静默放行**(它的原话:保证不了,请用户自己别并发),而且它在 **NFS 上
  > 根本不尝试加锁** —— 因为 `flock` 在 NFS 上即使给了非阻塞标志也可能**永久阻塞**
  > (rust-lang/cargo#2615),那是挂死,比失败更糟。
  > 我们没照搬"静默":工具撞上"没有锁"不是构建冲突重跑一次,而是**静默丢结论**,
  > 所以必须让用户知道。**只放行"不支持",不放行"没权限"** —— 后者是真错误。

### 4.8 源视频如何进入项目(`source.link`)

`init` 按"代价从低到高"依次尝试,并**把实际用了哪种记进 `project.json.source.link`**:

| 方式 | 代价 | 何时可用 |
|------|------|---------|
| `hardlink` | 零拷贝、零权限 | 同一卷(Windows 上建硬链接不需要管理员) |
| `symlink` | 零拷贝 | 需权限:Windows 要开发者模式或管理员 |
| `copy` | 占一份磁盘 | 兜底,永远可用 |

**为什么要记下来**:只有 `copy` 的项目是**自包含**的。硬链接/软链接的项目一旦离开原视频就废了 ——
"报告里能不能引用视频""项目能不能打包发给别人"都取决于这个字段。

硬链接的语义要注意:项目和原路径指向**同一个文件**,删掉原文件不影响项目,但**就地修改**
原文件会让项目看到新内容 —— 这正是 `video.meta.json.sha256` 存在的意义。

文件位置固定为 `source/video.<原扩展名>`(如 `.mkv` 就保持 `.mkv`,不改成 `.mp4`)。

**建项目时会先预判**:素材与目标目录是否同卷。不同卷则硬链接必失败,于是 **在动手复制之前**
就打印将要占用的空间和"把项目建到素材同卷"的具体命令 —— 几百 MB 的复制要好几秒,
不该让人干等到结束才知道在等什么。

**事后可体检**:`vidbrief status` 按 `source.link` 分别检查(见 §10.5)。区别很关键:

| 怎么进来的 | 会怎么坏 | 检查什么 | 坏了是什么级别 |
|-----------|---------|---------|--------------|
| `hardlink` | **不会坏**(数据在项目里) | 两边是否仍是同一份数据 | 源文件被移动/删除/替换都只是**提示**,不是问题 |
| `symlink` | **会坏**:源文件一移走项目就废 | 链接目标是否还在 | **✗ 必须处理** |
| `copy` | 不会坏 | 无需检查 | — |

> 为什么非要单独做这一步:`init` 时警告过一次之后,**再没有任何地方会提醒你**。
> 软链接的项目可能已经悄悄坏了几周,直到有人想看视频才发现。

### 4.9 补图候选 `supplement_requests.json`

```jsonc
{
  "generated_at": "...",
  "window": 3.0,                 // "附近有图"的判定半径(秒)
  "requests": [
    { "id": 1, "t": 18.8, "segment_id": 7,
      "text": "画面停住了大家可以把结论抄下来",     // 该段原文,让人一眼看出为什么被列出来
      "trigger": "no_shot_nearby",  // deictic_phrase | no_shot_nearby | both
      "nearest_shot": "s003", "gap": 3.2,
      "status": "accepted",         // pending | accepted | rejected
      "shot_id": "s004",            // accepted 时补出的截图
      "note": "画面停住后的定型画面,补一张便于读数" }
  ]
}
```

> 算法只负责**列候选**(指代性表达 + 时间距离),**要不要补由 agent 判断** ——
> 用户说"看这里"不代表真有个图要看。`status` 的初值恒为 `pending`。
>
> `status` / `shot_id` / `note` 是**状态的投影**(§4.10):工具写出来给人看,
> 判据在 `state.bin`。第五轮实测那次事故就出在这三栏上 —— 模型手写了整份文件
> (280 条 `reviewed_no_shot` + 18 条 `supplemented`,**两种值都不是合法枚举**),
> 而当时门读的就是这份明文,于是它瞎了、一路放行。

### 4.10 项目状态(`state.bin`)—— **非明文**

项目里唯一一个不是 JSON 的文件,装的是**推不出来的东西**:

| 装 | 不装 |
|----|------|
| `rev`(修订号)、`progress`(四步进度) | 报告在不在(看文件在不在) |
| `review`(用户确认 / 审核门,§4.2.1) | 转录原文(在 `transcript.json`) |
| 每张截图的 `status` / `reason` / `check`(看图结论) | 图是哪一帧、存在哪(在 `shots.json`) |
| 每段转录的 `conclusion` / `checked_at`(结论与核验戳) | 候选为什么被列出来(算法算的,在明文里) |
| 每条补图候选的 `status` / `shot_id` / `note`(处置) | |

#### 文件格式

```
偏移  长度  内容
0     9     magic "VDBFSTATE"
9     4     payload 格式版本(u32 LE;结构一改就 +1)
13    8     payload 长度(u64 LE)
21    32    payload 的 sha256
53    N     payload(bincode 编码)
```

**不加密。** 加密要密钥,而密钥无论放项目里还是放工具里,模型都读得到(工具就在它手上跑),
挡不住执意作弊,却多出一个"密钥丢了状态读不回来"的失败模式。
这里要的不是保密,是**改不动、坏了看得出来**:手写改不动这一坨二进制;
改了校验和对不上,工具当场报错,而不是把改过的内容当成真的接着往下走。

**版本不匹配也报错**,不做静默兼容 —— 和 `project.json` 的 `schema_version` 同一个道理:
"读到不认识的状态却继续跑"比"读不出来"危险得多。

#### 读不动的三态(这条是第五轮事故的全部差别)

| 情况 | 行为 |
|------|------|
| **不在** | 按**空状态**算(什么都还没核验 → 门全拦),但 `status` / `get_project` 要把这件事说出来 |
| **在、读得动** | 正常 |
| **在、读不动** | **报错**。每一件工具都拒绝开工,报错里点名去路(`vidbrief upgrade <项目>`) |

为什么"不在"不报错、而"读不动"报错:**"不在"推不出"被人拿掉了"** ——
新项目、手搓的项目目录都长这样,而且按空状态算是**最保守**的那头(拿不到任何便宜);
"读不动"则意味着**不知道谁审过什么**,只能按"都还没核验"算,而那正是要拦的方向。
两者都往保守那头倒 —— 这是那次事故唯一有效的教训:
`load().ok()` 把一份读不动的材料当成"没有",门数出 0 条、一路放行。

#### 内容底账:门的第①条是从文件里数数的

门的第①条数的是"**还有哪些没核验**",而它是从明文文件里数出来的 ——
**文件里没有的行,它当然看不见**。于是模型不必审 322 段:
把没审的那些从 `transcript.json` 里拿掉,门就以为活干完了。

> 用户当时问的是「门控不放过,它改了不还得改回去吗」——**改**是这样(改多了得改回去),
> **拿掉**不是:删掉了行,门反而看不见那部分活。这条是被一个专门的测试钉住的
> (`removing_rows_from_the_plaintext_must_not_hide_work`,先红后绿)。

所以状态里给三份材料各记一份**内容底账**(`ContentPrint`:几条 + 内容的 sha256),
外加**步 3 的那份总结**(`03_summary/summary.md`,它守的是步 3→4 那道门,见 §6.1.2):

| 记什么 | 不记什么 |
|--------|----------|
| 转录:段号 / 区间 / 正文 + 时长与模型 | 结论、核验戳(那是状态) |
| 截图:哪一张 / 哪一刻 / 存在哪 / 从哪来 | 留用还是弃用、看图结论 |
| 候选:候选号 / 时刻 / 指向哪一段 / 那段原文 / 触发原因 | 处置结论与理由 |
| 总结(`summary.md`):正文逐行 | ——(它没有"投影那几栏") |

**按内容算,不按文件字节算**:换个缩进、重排键序不算材料变了(那是同一份内容换个写法),
改一栏**投影**状态也不算(那本来就允许人手改)。

门开口之前先对一遍;对不上就拦,并且点名两条去路:

```bash
vidbrief preprocess <项目>                          # ① 重跑产生它的那一步,把工具算的那份找回来
vidbrief upgrade <项目> --accept-material           # ② 显式认下现在这份(会报出重记了哪几份、原来几条现在几条)
```

**底账默认不换**:材料被人改过时,不显式说 `--accept-material`,`upgrade` 只会把话说清楚
(`底账没动 —— 它跟现在这份对不上(底账 322 条,现在 22 条);要认现在这份,加 --accept-material`)。
不然底账就成了摆设 —— 而它挡的正是"把没审的行拿掉"这件事。

`vidbrief status` 会把对不上的地方列成 ✗ 行(`materials.content_stale`),并以此定非零退出码。

#### 明文文件退回"投影"

`shots.json` 里那几栏、`transcript.fixed.json`、`supplement_requests.json` 里那几栏,
**只是上一次写出去的样子**:

- **读**:先读明文里的**内容**,再把状态盖上去(工具、视图都走这条路);
- **写**:调用方改完那份合并过的对象再交回来,内容进明文、状态进 `state.bin`,**同出一源**;
- **对不上时**:`vidbrief status` 把它们列出来给人看(`projection_stale`),
  但**门不看** —— 手改投影骗不过门。

**为什么保留投影**:转录要能直接读、时间线要能画、人要用编辑器翻;而且它是一份
"上次工具写出去的样子"的留档。但它**不驱动任何判断**。

#### 两条给人和 agent 的出口

```bash
vidbrief upgrade <项目>           # 旧格式迁过来 / 状态文件不见了读不动时重起一份
vidbrief upgrade <项目> --fresh   # 什么都不收,状态清零(材料原样保留)
```

`upgrade` 的产物永远是**最保守**的那一份:读得到什么就收什么,读不到的就是"还没核验"。
**拿它绕门是绕不过去的** —— "还没核验"只会让门拦得更死。所以就算这条命令行
模型自己也跑得动,它也不构成一条捷径。

## 5. 步 1:前处理(**一件作业,三个入口**)

> MCP 工具:`preprocess`(起作业并等它)/ `preprocess_progress`(看进度)/ `preprocess_result`(取结果)。
> **一次作业做完全部产出,无中间态、无中断、不调模型** —— 但「一次作业」与「一次调用」
> 从 2026-09-26 起**不是同一件事了**(见 §5.4)。

### 5.1 完成三件事

**① 差帧图** — ffmpeg 按 `fps=1`、`scale=480:-1` 抽帧;逐帧算 8-bin/通道 RGB 直方图 + 亮度均值;与上一帧差分 → `score` → `change_curve.json`。

**② 语音转文字(带时间戳)**
1. `ffmpeg -i video.mp4 -ar 16000 -ac 1 -c:a pcm_s16le audio.wav`
2. `whisper-cli.exe -m ggml-medium.bin -l zh -f audio.wav -otxt -osrt -ovtt -of transcript`
3. 解析 SRT → `transcript.json`。
   - 已知局限:中文专有名词必错(实测「达摩院」→「打墨院」、「派森」→「Python」),**由 agent 在步 2 纠错**。

**③ 预筛选关键截图(纯算法,基于差帧图)**
- 取**"变化密集区"的代表帧**,而非只取孤立峰值——信息密集段(连续演示、多图快切)在差帧图上表现为一段高值区。
- 算法见 §5.2;截图质量:宽度 ≥1280px、JPEG q85、文件名带时间戳。

### 5.2 密集区截图算法

```
输入: changes[] (t, score), 采样间隔 ≈1s
参数: W = 8s(窗口), PEAK_THRESH = 0.25

1) 滑窗累计: mass(i) = Σ_{j∈[i-W/2, i+W/2]} score[j]      // 居中窗口,见下
2) 标定阈值: MASS_THRESH = max(中位数 × k, 绝对下限)        // 防止静止视频全被选中
3) 密集区:        mass 连续超阈值的极大区间 → 回退半窗 → 按"贡献下限"修边
4) 孤立硬切换:    score ≥ PEAK_THRESH 且 邻域均值远低(突出度 ≥ 3×),且不属于任何密集区
5) 长静止打断:    长时间静止(>120s)后首次变化 → 重新标注为章节起点
6) 每区取代表帧:  密集区取区间峰值(区间比窗口长时两端各补一帧);孤立峰取峰值;长静止取变化后首帧
7) ffmpeg 精确抽帧 → shots/sXXX_tttt.jpg + shots.json
   **纯色帧照样截,但预标 `drop`**(2026-09-26):抽之前花一次小解码算这一帧的亮度方差
   与直方图,纯色(切黑 / 片尾淡出 / 纯色占位)把图截下来、`status = drop`、
   `reason` 写明是纯色与怎么翻回来。**为什么不干脆不截**(实测当场改的口径):
   `fixtures/test_sample.mp4` 的三个切换点**就是纯色帧** —— 不截的话"切换点必须命中"
   这条 M1 验收标准当场作废。**一次画面切换是事件,黑屏也是那个事件的证据。**
   省的是**注意力**(弃用的图不进"待校准"那一批,门不拦它),不是材料
   (`vidbrief-core::extract::flatness_at`;判据是纯函数 `FrameFeature::is_flat`,
   阈值取得很保守,见那边的注释:误杀真图的代价比漏放一张黑图大得多)
```

实现要点(`vidbrief-core::regions`,**纯函数**,不碰进程):

- **窗口居中**:若窗口往后看(`[i, i+W)`),一个尖峰会让它**之前**的所有窗口都超阈值,
  区间整体前移 —— 定位出来是错的。居中窗口的 `mass[i]` 才表达"i 附近有多热闹"。
- **修边**:居中窗口会把区间向两侧摊平半个窗宽。修边依据是**贡献下限** =
  `MASS_THRESH / 窗口样本数`,即"每帧至少要贡献这么多才撑得起这个阈值"。
- **突出度**(`PEAK_PROMINENCE = 3.0`,沿用旧实现 `src/main.rs` 的实测值):
  `score ≥ 邻域均值 × 3`。这是 §5.2 里"邻域均值**远低**"的可操作定义。
  **少了它会出事**:回归素材前半段有个每 4 秒一次的小动画(0.26–0.28),刚好越过
  `PEAK_THRESH = 0.25`,会被逐个误报成硬切换。
- **长静止是"重新标注"而不是独立判据**:同一个事件,"长时间静止后的首次变化"
  比"一次硬切换"信息量大(它说明这是**章节边界**),所以优先用前者标注。
- **静止判据是派生值**:`static_level = PEAK_THRESH × 0.2`。现在没有真实数据能标定它,
  先不暴露调不动的旋钮。
- **单帧不算密集区**:一次硬切换会让它前后共 `2×half+1` 个窗口都超阈值(每个窗口里都有
  那一个尖峰),很容易被误判成"一段热闹"。按定义密集区要**持续**活跃,单点交给孤立峰判据。

### 5.2.1 在真实长视频上的标定结果(2026-09-24)

用样本 D(985 秒)验证,
对照是**两条独立路径**:

1. ffmpeg 自带的场景检测(`select='gte(scene,0)'`),阈值 0.15;
2. `tools/whisper/demo.srt` 里那几个时刻**人在讲什么** —— 每个检出点都落在一次主题切换上。

| 结论 | 数据 |
|------|------|
| **不漏** | 检出 11 个区域,与对照的 11 个切换点一一对应 |
| **不假阳** | 阈值下方最高分 **0.0569**,离 `peak_threshold = 0.25` 有 **4.4 倍**分离度 |
| **比对照更灵敏** | `t=192` / `t=240` 两处 ffmpeg 在阈值 0.15 下**漏了**(它们的 scene 分正好 0.102),本工具找到且转录证实那里在换图/换论点 |
| **时序误差** | 持续 **+0.4~0.9 秒**,即 1fps 采样的量化误差(切换在 478.60,只能在 479 采到) |
| **性能** | 985 秒全程(抽帧+评分+密集区+抽 11 张图)**7.3 秒**;流式实现只留两个特征向量,不存 380MB 像素 |

**时序误差是良性的**:峰值取的是变化后的**第一个**采样点,所以截出来的图总是切换**之后**
那一侧 —— 正是要给人看的新内容。只是记下来的 `t` 比真实切换晚最多一个采样间隔。

**还没标定的**:`mass_k` 在这条视频上从未生效(中位数 0.0115 × 3 = 0.0345 < 下限 0.6,
下限全权决定)。也就是说**自适应那一支没有真实数据检验过** —— 它要等一条"背景一直有噪声"
的视频(如摄像头录屏)才能验。

### 5.4 作业与调用分离(2026-09-26,清账五)

**问题**:宿主给每次 MCP 调用的上限实测是 **5 分钟**,而步 1 真跑过一次 **4 分 23 秒**
—— 差 37 秒就被掐。而一旦被掐,那次活干到哪儿了、要不要接着做,谁都不知道。

**做法**:作业跑在**独立进程**里(`vidbrief preprocess <项目>`),调用只是「看着它」。
和查看服务挪出工具进程是同一个道理:**工具进程是会话的,作业是项目的**。

| 工具 | 干什么 | 什么时候用 |
|------|--------|-----------|
| `preprocess` | 起作业(没在跑的话)+ 等它,默认最多等 180 秒 | 开工;等够了就再调一次接着等 |
| `preprocess_progress` | 只看一眼(只读、不等) | 想知道还要多久 / 不想占着一次调用 |
| `preprocess_result` | 取结果 | 跑完之后 |

几条定死的规矩:

- **等够了不等于没做**:`preprocess` 等到预算用尽就如实报「还在跑 + 当前进度」,
  **不重开**;再调一次是接着等。会话被掐、进程被杀,作业照跑(它不靠调用活着)。
- **跑完了才重跑**:盘上那趟已经结束时,再调 `preprocess` 才是**新的一趟**;
  还在跑时调用只会搭车 —— 「不重开」是这里最容易搞错的一条。
- **进度通知**(`notifications/progress`,客户端要给 `progressToken`):五步制
  (开工 / 差帧图 / 抽帧 / 转录 / 渲染 / 完),抽帧那一段带细粒度张数。**转录那几分钟
  没有细粒度进度可报**(whisper 不给),那一段就只报「开始了」并说清它最久 ——
  假装有进度比没有进度更坏。
- **作业的输出不走管道**(stdout / stderr 都丢掉)。实测踩过:会话一退,管道读端消失,
  作业往里面写进度**当场 panic** —— 一项跑了几分钟的活就这么没了。
  它的输出去处是**运行记录**。

**运行记录** `01_preprocess/run.json`(`vidbrief-ops::run`):

```json
{
  "run_id": "20260927-001750-24740-1",   // 这一趟的名字(起它的人定,认人用)
  "project_id": "test-sample",
  "stage": "shots",                        // starting/analyzing/shots/transcribing/rendering/done
  "message": "抽关键截图 12/57",
  "error": null,                           // 有值 = 这一趟失败了(原因)
  "warning": null,                         // 写锁降级之类"必须开工前说出去"的话
  "options": {"fps": 1.0, "width": 480, "transcribe": true, "shots": true},
  "pid": 24740,
  "started_at": "…", "updated_at": "…", "elapsed_seconds": 41.2,
  "shots_done": 12, "shots_total": 57,
  "report": null                           // 跑完时是完整的 PreprocessReport
}
```

三条要留意:

1. **记录里写的 ≠ 读出来的判断**。记录停在「还在跑」而进程早没了(断电、`kill`、休眠),
   要靠**心跳**认出来:每 2 秒推一次 `updated_at`,超过 120 秒没有动静就判「断了」
   (`RunOutcome::Interrupted`)。转录那几分钟没有任何进度回调,心跳是那一段唯一的声音。
2. **它是过程投影,不是材料** —— 材料以 `state.bin` 与各材料文件为准(§4.10、§6.1.2),
   所以它没有 JSON Schema,也没有内容底账。写不动(磁盘满、目录只读)**不许拦作业**。
3. **写锁在作业进程手里,不在会话进程手里**。会话只读记录;真要写项目的还是跑作业那个进程,
   它取锁、写材料、放锁,一次调用一把(§4.7)。两个会话同时开工时,后到的那个在锁上被挡,
   不会写出第二份记录(`RunRecorder::start` 也拒绝在一条活记录上再开一趟)。

### 5.5 增量重跑:输入没变就不重算,更不作废成果(2026-09-27,清账六)

**问题**:从前 `preprocess` 一律重算,而且**重算就作废成果** —— 画面重算清空全部看图结论
(`state.shots.clear()`),转录重跑清空全部核验戳(`state.segments.clear()`);作废掉多少
就写在报告的 `shot_checks_cleared` / `segment_checks_cleared` 里。而校准(模型逐张看图、
逐段核验)是整套流程里**最贵的活**:手滑重跑一次、改个参数试一下、中途失败重来,
几十分钟的模型工作当场归零 —— 那两百多秒的算法只是小头。

**做法**:两半**分开判**,各自比输入指纹(记录落在 `01_preprocess/inputs.json`):

| 那半 | 输入是什么 | 沿用还要额外满足 |
|------|-----------|-----------------|
| 画面 | 源视频 sha256 + `fps` + `width` + 抽帧分析口径版本 + 工具版本 | 三份材料(`change_curve.json` / `dense_regions.json` / `shots.json`)都在、读得出、**清单里每张图都在盘上**、清单内容与**内容底账**一致 |
| 转录 | 源视频 sha256 + 模型 + 语言 + 转录口径版本 + 工具版本 | `transcript.json` 在、读得出、内容与底账一致 |

逐项相同才沿用;**任一项说不清就重算**(没记录、材料不在、读不动、底账对不上、版本不认识)。
方向是定死的:重算只是多花几分钟,**拿旧材料配新视频才是真出错**。

五条要留意:

1. **源视频 sha256 每次当场重算**,不读 `project.json` 里 init 时记的那个。项目里的视频
   常是**硬链接**,源文件被就地改时两份是同一份数据 —— 只有重算才发现。对不上时除了不沿用,
   还会**单独报一句**(`reuse.source_changed`):那意味着整套材料都可能不可信。
2. **源视频指纹每半各存一份**,不在顶层合成一个。差别在这条路上:「换了视频、这趟只跑转录」
   —— 那时画面那半的成果还是**旧视频**跑出来的,它得留住旧指纹;顶层共用字段表达不了这件事,
   下次就会拿「新视频指纹 + 旧截图」当成一套,把旧帧当新帧用。
3. **「上一次是拿什么跑出来的」是记录,不是判据**(所以它没有 JSON Schema,也不进 `state.bin`)。
   它被人手改的后果最多是**多算一次**;真正判「东西还在不在、还是不是那一份」的是
   内容底账(`state.content`,M4 那套),判据不依赖这份明文。
4. **复用与作废一样要报出来**:`PreprocessReport.reuse` 说清沿用了哪半、没沿用的原因
   (指名到哪一项变了),CLI 照打。静默作废别人的活最不该干 —— 静默复用同样不该。
5. **`--force`(CLI)/ `force: true`(MCP)无条件重跑**。「能省则省」不能变成「没法强制重来」:
   怀疑上次那批材料、或想干净地重来一遍时走这条。
6. **复用只管「这一步要不要重算」,不管「哪些成果不要了」。** 模型在步 2 里的判断
   (把某张图弃用、给某张写下看图结论)住在 `state.bin` 里,沿用那条路上**一个都不碰** ——
   留用 / 弃用永远是它说了算;只有真重算(输入变了 / `--force`)才作废那些结论,
   理由也是硬的:重抽之后它们说的是旧帧。判据:`reuse_never_touches_what_the_model_decided`。

**不做跨项目复用**。项目目录是这套设计里唯一自包含的单位,而看图结论还绑着「第几轮看的、
谁拍的板」—— 把 A 项目的判断搬到 B 项目,等于用别人的眼睛替自己做证。真要多版本,
该走的是克隆项目,不是共享缓存。

**判据**(端到端在 `crates/vidbrief-cli/tests/preprocess.rs`,判据函数在 `vidbrief-ops` 单测):
同样的输入二跑 → 报告说沿用、**截图文件的修改时间一个没变**、`shot_checks_cleared` 为 0;
只改 `fps` → 画面重抽、理由指名 `fps`;源视频加一个字节 → 两边作废并单独报出;
`--force` → 明明一个字没变也重抽(复用那套的反面对照)。判据函数十来条单测,
每条「不能沿用」都配一条「照做就能过」的路径。

## 6. 步 2:校准(迭代工具组)

> **没有"一次运行完的 calibrate"。** 校准 = agent 反复执行 **"取材料 → 自己看图判断 → 把结论存回"** 的循环,由用户对话驱动。

**本步的定位:核心目标就是解决"识别错误"。** 两类错误:

1. **语音识别错误(ASR)**:同音错字、专有名词听错(实测「Python」→「派森」、「达摩院」→「打墨院」)。
2. **画面识别错误**:看图看错对象/规格/状态,或图与语音对不上。

**自动修不好的,由兜底机制处理——"审查节点"**(即用户与 agent 的对话):用户直接指出"这里还是错的 / 应该是 X",让 agent 立即改。校准的迭代本质,就是 **"自动纠错 → 人工审查 → agent 再改"** 的往复。

### 6.1 循环的三个动作

**校准 = 把材料改对。** 不是"在旁边记笔记" —— 判断要落成材料的改动,
否则用户拿到的是一份待办清单,不是结果。所以核心是这三件事:

| 改什么 | 工具 |
|--------|------|
| **把错的改对** | `apply_corrections`(转录纠错 → `transcript.fixed.json`) |
| **把缺的加上** | `extract_shot` / `request_shot`(补图) |
| **把多余的删掉** | `update_shot(drop)`(废图:全黑、重复、糊到看不出) |

围绕着它们的是三类辅助动作:

| 动作 | 工具 | 谁在做 |
|------|------|--------|
| **取材料** | `get_shot`(返回图像)、`get_transcript`、`list_shots` | 工具(供) |
| **看图判断** | —(agent 内部多模态推理) | **agent** |
| **记下判断** | `record_shot_check` | 工具(存) |
| **列候选** | `find_supplement_candidates` | 工具(算) |

**工具不判断对错,只搬运与保存。** 判断是 agent 的,改动是 agent 让工具做的。

#### 6.1.1 出口有一道门:数的是**核验状态**,不是签字

**校准这一步的每一项只有三种状态**:

| 状态 | 谁定得了 | 门怎么办 |
|------|---------|---------|
| **已核验** | — | 不拦 |
| **还没核验** | **模型自己**(接着审就是了) | 拦,告诉它还差哪几条。**不扯上人** |
| **核验过、要用户拍板** | **人** | 拦,告诉它等的是哪几条 |

`write_summary` 之前数一遍:

1. **有没核验的 → 拦。** 报错列出还差哪几条,让模型接着审 ——
   不打断 agent loop,我们只给反馈。**这一条防的是"跳过了 300 段还想过"**,
   也是门最主要的一档。
2. **有要用户拍板的 → 拦。** 模型可以去问用户,问完把决定落到**条目**上;
   用户说"这些我知道,就这样过",那句话进 `approve` 的 `note`。
3. **全核验完、没人等着 → 放行。不需要任何人签字。**

第 3 条是关键:**门管的是"有没有跳过步骤",不是"有没有人点头"。**
要不要在节点上停下来问用户,是模型照用户最初那句交代决定的(判断归 agent)——
用户说"每个节点找我确认",模型自然会在全绿之后仍然停一停;说"全程托管只看结果",
就一路做下去。**门在这里不该替用户做决定,也不该给他添麻烦。**

#### 门上的每一条规则,以及消掉它的那一步

规则一多,最怕的不是某条错,而是**两条各说各的**(体检说没事、门却拦着),
或者**拦下来说不出去路**。所以这张表是硬要求:每加一条规则,都要在"去路"那一栏
写得出一个具体的动作,并在测试里有一条"照做就能过"。

| # | 规则 | 什么时候触发 | 消掉它的那一步 |
|---|------|--------------|----------------|
| ⓪ | **材料不是工具写出去的那一份了**(内容底账对不上,§4.10) | 材料被手改 / 被拿掉 / 少了几行 | 重跑产生它的那一步(`preprocess`、`find_supplement_candidates`),或 `vidbrief upgrade --accept-material` |
| ① | 还没核验(截图 / 转录段 / 补图候选) | 有没审完的 | `record_shot_check` / `apply_corrections` 的 `reviewed` / `disposition_supplements` |
| ② | 看图结论的**凭据**对不上材料 | 图不在了 / 引的那句话不在材料里 | 重看一眼那张图,给一句**照抄**的 `evidence_quote` |
| ③ | 有"核验过、要用户拍板"的项 | 模型自己说没把握(`confidence: low`) | 问过用户、把话落到条目上;或 `approve` 记下"他说先这样" |

三条**不拦、只报告**的(它们是给人看的,不是门):

| 规则 | 出现在哪 | 谁能发现 |
|------|---------|---------|
| 明文投影与状态对不上(那几栏状态被手改) | `vidbrief status` 的 ⚠️ 行 + `materials.projection_stale` | 门不看它;下一次写这份材料的工具调用会盖回去 |
| 状态文件不在 / 读不动 | `status` 的 ⚠️/✗ 行 + `materials.state_status` | 读不动时**每件工具都拒绝开工**(§4.10) |
| 材料文件在、但读不动 | `status` 的 `materials.unreadable` | 工具当场报错并点名重算那一步 |

每一项的三种状态从哪读(形状见 §4.5 与 §4.2.1)。**读的是 `state.bin`(§4.10),
不是明文材料** —— 明文那几栏只是投影,谁都能改,而判据不能是能随手写的东西:

| 项 | 已核验 | 未核验 | 要用户拍板 |
|----|--------|--------|-----------|
| 截图 | `check` 有 | `check` 为 `null` | **模型自己说没把握**(`check.confidence == "low"`) |
| 转录段 | `checked_at` 非空 | `checked_at` 为空 | `conclusion.outcome == uncertain` |
| 补图候选 | 已接受或已拒绝 | 还是 `pending` | ——(要不要补,模型自己定得了) |

**门的边界(要说清它挡不住什么)**:门管的是**走工具的路径**。宿主可能给 agent
配上自己的文件工具(read/write/exec)—— **读,欢迎**(材料即接口,项目文件本来就该能直接读);
**写,挡不住** —— 那工具不在我们手里。能做的只有三样,而且都做了:

1. `instructions` 硬规矩第 4 条:**材料与结论一律经工具改**(写总结、改转录、动 shots.json);
2. **改出来会被认出来**:绕过工具改的明文与 `state.bin` 里的内容底账对不上,
   下一次开门就是⓪那条拦下(§4.10)—— 机制本身就是最好的劝阻;
3. 文档写明白(就是这一段)。

实测(M5 真 agent 两轮):agent 确实会开局 `exec dir` 把项目翻一遍 —— 那是它的自由;
两轮最后都是从 `write_summary` 落的盘。

#### 6.1.2 步 3→4 那道门:出报告之前,总结得是**工具写出去的那一份**

**同一个机制,快照对象换成 `summary.md`**(M4 之后挂账,[260926-10](../devlog/2026-09.md) 做掉):

| # | 规则 | 什么时候触发 | 消掉它的那一步 |
|---|------|--------------|----------------|
| ① | **还没有总结** | `summary.md` 不在 / 是空的 | `write_summary` |
| ② | **总结不是工具写的那一份**(没有底账,或内容对不上) | 手写、手改、被拿掉 | 把现在这份正文交回 `write_summary` 再落一遍(内容一字不改也行) |

它挡的是两种"跳步":**没做步 3 就出报告**,以及**拿一份谁都没看过的稿子出报告**
(M4 第三轮真 agent 的实测形状:审核门关着,它拿宿主的文件工具把 `summary.md`
整个写了出来,然后接着往下做)。

**这里没有"等人拍板"那一档。** 步 2 的门有三档,因为校准里"我没把握"是模型自己
说得出来的状态;总结没有"没把握"这回事 —— 一版总结要么是这个说法,要么是另一个说法。
**要不要写完停下来等用户点头,是模型照用户那句交代决定的**(与 §6.1.1 同一条道理):
说"每个节点找我确认"就停,说"全程托管只看结果"就一路做下去。

门在这里只保证一件事:**出报告用的那份总结,和用户在对话里看到的那份是同一份。**

> **数据那一层另有一道机械校验**(`build_report` 写盘之前,与门同一个位置):
> 知识点引的截图/转录段必须存在、外部来源的链接必须点得开、`t` 必须在视频里。
> 它挡的不是"跳步",是**引的东西不存在** —— 页面上那会是一张打不开的图、一条点不开的链接。
> 详见 §8 的"报告数据"。那**不是**门的一部分:门管步骤的边界,这里是数据的形状与凭据。
>
> **讲者那侧不校验了**(2026-09-27 起):从前的规矩是"照抄一句原话,工具去转录里搜,
> 搜不到拒收",本意是拿它当"这句话确实在材料里"的机械证明。实测(一次真 agent 跑)连着
> 退回五次,五次全是**抄写翻车**:掉字、换近义词、跨段拼句,甚至把 ASR 的错字"顺手改对"了
> (转录是「奔发」,它照上下文写成「爆发」)—— 那本来是校准该夸的事。而段号模型**本来就给**
> (`segments`),工具一秒钟就能取到原文。**机械的活留给工具,别让它转手。**

状态**读不动**时门按最保守那头算:每件工具都拒绝开工,报错点名
`vidbrief upgrade <项目>`(见 §4.10)。那次事故的全部差别就在这两个方向之间:

| 遇到 | 按哪头算 | 结果 |
|------|---------|------|
| 读不动 → 当成"没有" | 最松 | 门看不见那 298 条候选,**一路放行**(实测事故) |
| 读不动 → 按"还没核验" | 最保守 | 门拦住,而且说清怎么自救 |

判 `drop` 的截图不用核验 —— 它不进总结,没人关心画面上是什么。

**截图的"要用户拍板"只有一个判据:模型自己说它没把握(`confidence: low`)。**
**不是** `needs_review()`,也**不是** `issues` 非空 —— 那两样问的是另一个问题:
"这张图值不值得人看一眼"(视图口径,现在叫 `list_shots` 里的 `needs_look`)。
`issues` 非空的意思是「**我有话要说**」,不是「我定不了」。

> 这条是 M4 第四轮真 agent 联调逼出来的:那一轮 7 张卡在"要拍板"的图里
> **没有一张是把握低**,全是模型如实写下的观察(「画面无标题文字,本节标题无法核实」),
> 而它给它们**全打了 `high`**。拿 `issues` 当判据等于**诚实反而过不去门** ——
> 模型照要求如实写「看不出来」,就永远到不了"已核验";要过门只剩两条路:
> 把观察抹掉,或者签字。而门自己的报错里写着「别把发现改成没发现」。**它选了签字。**

> **「要用户拍板」这一档不是新造的**:转录那边,`uncertain` 类型的文档原话就是
> "agent 认为这里可能有问题却不敢断言" —— 那句话本身就是模型在说"我定不了";
> 截图那边的 `confidence: low` 同理。**两边的判据都落在"模型自己承认拿不准"上,
> 而不是落在"我从中推断出它大概拿不准"。**
>
> **为什么 M0 说"不设审核门",M4 又加上了**:当初的理由是"编排在 agent 侧,放行是对话行为"。
> 联调跑了两轮之后发现,靠对话把关等于没有把关 ——
> **一个一张图都没校准的项目可以直接写总结、把步 3 标成完成**,而没有任何人会发现。
>
> **门之后改过两次,两次都是"做重了"**:
> 第一版拿**四项计数**当判据([260925-21](./devlog/2026-09.md))—— 而校准里最常干的
> 一件事是**改字**,一项计数都不动。
> 第二版换成**逐条内容摘要**([260925-24](./devlog/2026-09.md))—— 判据准了,
> 却把"用户签字"设成了**必需**,于是工具没法无人值守地跑。
> 第三版才是现在这样:**门按核验状态判,签字降成"带着要拍板的项过关"的一把钥匙**
> ([260925-25](./devlog/2026-09.md))。
> 一路的教训是同一句 —— **判据要照"我想拦住什么"选,不能照"我数得出什么"、
> 更不能照"我手上正好有什么机制"选。**

#### 6.1.2 写操作只有一条序列(`ops::with_write`)

凡是改项目文件的活,都走同一个函数:**开 → (必要时取锁) → 做**。

```rust
vidbrief_ops::with_write(project_id, lock, |opened, lock_note| { … })
```

- `lock` 决定怎么写锁,**因为锁的持有期是入口的事**(§4.7):
  CLI 传 `None`(现取一把,命令结束就放);调用方已经把锁拿在手上的入口传 `Some(&guard)` ——
  它收的是**真凭证**而不是布尔:想走这条支路,手里必须真有一把 `LockGuard`。
- 那句"文件系统不支持锁"的说明交给**闭包**,不是当返回值 ——
  因为该说的时机不同:`preprocess` 要跑几分钟,那句话必须在**开工前**说。

> 为什么要收:这条序列原本在四个地方各写过一遍,**而抄的时候漏了两样**
> —— 页面按钮那条既没走进程内排队、也没带降级警告([260925-21](./devlog/2026-09.md)),
> 而 Cargo 和编译器都不会提醒。以后往序列里加任何一步都会自动落在所有入口上。
>
> MCP 那两条入口还多一层**入场**(`State::enter_write`:确保持锁 + 记账 + 发一张
> `WriteHold` 凭证;凭证 drop 时交回计数、数到 0 才放锁),
> 那一层在 `vidbrief-mcp` 里,两个入口共用同一个函数。

### 6.2 四个子任务(agent 视角)

**① 图文匹配 + 音画同步**
- agent 调 `get_shot(shot_id)` 拿到**图像本身** + 该时刻前后转录(±6s)。
- agent 自己看图、对照转录,得出结论,调 `record_shot_check` 写回:
  ```
  { match, audio_visual_sync, type_read, neighbor_text, issues[], confidence }
  ```
> **`match` 的语义写死(2026-09-26)**:判的是「**画面讲的与同期转录讲的是不是同一件事**」
> (主题 / 动作 / 对象);**用字层面的差异不算不符** —— 转录把一个字听错了,那是②那条
> 转录纠错的活。判据一句话:「这段话配这张图,读的人会不会觉得对不上」。
> 写死的理由:这种"两种读法都说得通"的字段,实测被两个模型填成了**相反答案**
> ([260925-20](../devlog/2026-09.md));说法在 schema、工具入参与 P1 三处对齐。
> 依据(RESEARCH.md 5.5b):单看图会把「样本 15 分钟」臆断成「结构」;图 + 同期转录一起判断,会服从转录、诚实标注"画面无法确认",并主动指出"转录提到 ETC 但画面只有样本"这类矛盾。**这是 agent 的判断,工具只负责把图和文一起递给它。**

**② 转录纠错(ASR 术语校正)**
- agent 调 `get_transcript` 读全量,自查同音错字/专有名词,用 `apply_corrections` 逐条写回。
- **优先依据画面文字**:截图里常直接写着正确写法(如「Python 列表」),agent 应把画面文字当纠错基准;上下文语义次之。
- **术语表默认关闭、可选**:若用户额外提供一份正确写法的领域词表(如 `[样本, PYTHON, 索引, …]`),agent 用它做对照;不给则自行判断。
- 产出 `transcript.fixed.json` + `transcript.diff.md`(人可核对)。
- 校对规则(写进提示模板 §10.4):只改明确识别错误,不润色、不改语序;数字/单位/时间保留;无把握标 `uncertain` 不臆造。

**③ 图文交叉印证**
- agent 综合 `transcript.fixed` 与 `shots.json` 里全部 `check` 结论,自己列出矛盾点,写进 `cross_validate.md`(通过 `write_note` 之类的写入工具)。

**④ 补充截图(算法漏掉的)** — `find_supplement_candidates`(纯算法)+ `extract_shot`
- 算法扫描转录里的**指代性表达**("如图/这个图/看这里/这边显示/大家看屏幕/这一段/形态")及"提到但附近(±3s)无截图"的时刻 → `supplement_requests.json`。
- agent 判断哪些确实需要,调 `extract_shot` 补帧 → `shots_extra/`,登记进 `shots.json`(`origin=agent_request`)。

### 6.3 迭代形态(对话怎么进行)

```
用户: 把这个视频做成图文总结
agent: → create_project → preprocess          （纯算法,一次做完,几分钟）
         → list_shots → get_shot(逐张)【自己看图对照】
         → 把材料改对:apply_corrections / extract_shot / update_shot
         → record_shot_check(每张) 记下判断
         → render_timeline() 把链接给用户
         "11 张看完,改了 4 处转录;链接在这儿,你看一眼"
用户: 第6张重新截 602 附近;另外"派森"应该是"Python"
agent: → extract_shot(602) → get_shot(新)【再看】→ 呈现
       → apply_corrections([...]) → 呈现 diff
       → 重渲染
用户: 都对,继续
agent: → approve()        ← **这一步不过,下面写不了**
         → write_summary()  （步 3 开始）
```

三件事值得注意:

- **停下来不是请用户批准动作,是把改完的结果拿给他看。** 该改的已经改完了,
  他看的是成品;要改哪儿他再说 —— 那是下一轮。
- **`approve` 是针对某个具体版本的。** 之后再动任何材料,这次确认就作废
  (见 §6.1.1),得重新看一眼再确认。多轮迭代因此天然对齐。
- 每轮改动写 `calibration_log.md`(哪轮、改了哪张图/哪段字、为什么),
  每轮后重渲染时间线。

## 7. 步 3:总结(agent 探索 + 原子产出)

> 相对原子:agent 自主探索后一次写出总结;允许用户拿到一版后带新提示重做。

### 7.1 agent 可用工具

| 工具 | 作用 |
|------|------|
| `list_shots` / `get_shot` | 看有哪些截图、**把图递给 agent 看** |
| `search_transcript` / `get_transcript` | 转录检索/读取 |
| `list_regions` | 密集区清单(决定聚焦哪段)。**建结构的首选** —— 它的密度量纲就是"这段热闹" |
| `get_change_curve` | 差帧图原始点(986 个 `(t, score)`)。**建结构时不必读** —— 那是噪音,而结论已在密集区里;要看分布时才用 |
| `request_shot(t, reason)` | **补图**:发现缺画面时临时抽帧(同 `extract_shot`;补来的图要用 `record_shot_check` 记结论,门一视同仁) |
| `write_note(path, md)` | 写中间笔记(只写 `02_calibrate/` 与 `03_summary/` 下的 `.md`;`summary.md`、`transcript.diff.md` 有专属工具,这里写不了) |
| `write_summary(t?, title, md)` | 交**一段**(有 `t` 的上时间轴,没有的作总述);同名再交 = 改写那段。段落落在 `03_summary/sections.json`,`summary.md` 是拼好的文章 |
| (agent 自带) | 联网检索背景知识(术语、事件、对象) |

### 7.2 建议的探索策略(写进提示模板 §10.4;M5 按联调实测打磨过)

1. **先读全局**:转录 + 密集区 + 截图清单 → "总—分"框架。
   差帧图原始点不必读(986 个数字对建结构是噪音)—— 它的结论已经在密集区里了。
2. **再核局部**:对候选关键段,`get_shot` 看图 + 读同期转录,**agent 图文印证**。
   `get_shot` 返回里带着校准阶段的旧结论 —— 可参考,但要自己看过图再引用。
3. **缺口驱动补看**:语音提到某形态/图表却没图 → `request_shot`;外部知识缺口 → 联网检索。
4. **边看边记**:每主题写 `notes/`,保留引用来源(截图 id + 转录时间戳)。
5. **汇总**:`write_summary`。已有旧稿时先读旧稿再改(§7.4)。

### 7.3 溯源要求

总结里每个结论应可追溯:**截图 id + 转录时间戳**,便于回跳原视频与人工抽查。

### 7.4 二次修改

用户不满意时给新提示("第 3 个案例补上数值区间和形态"),agent 带旧 `summary.md` + 新材料重做,覆盖或另存新版本。

#### 8.1.1 风格:轮廓在 `skill/` 里,工具只记「点了哪一种」

用户的提示词里带着他要什么 —— 给谁看、要多细、什么语气、要不要例子。
**光把要求存下来没用**:存一个"我是大白话"的标签,内容并不会因此变成大白话。
真正决定内容的是**轮廓**:讲几点、每点按什么顺序写、要不要证据、术语解释到什么程度。

**轮廓的定义住在 `skill/` 里,不住在代码里**([260926-16](../devlog/2026-09.md)):

```
skill/
  SKILL.md      入口:这套技能管"怎么写",工具的契约在 get_guide(两边不许互相抄)
  workflow.md   流程与规范:选点、图文互证(含 §0.1「指着画面说」的话术表)、溯源、每条骨架、踩过的坑
  styles.md     风格:定义轮廓的七维 + 五种预置风格(怎么填)+ 按用户的话怎么挑
  tools.md      工具速查(**自动生成**:从活的工具表渲染,有测试盯着不许过期)
```

**为什么是文档不是代码**:手艺会变(条数怎么换算、每条什么骨架、加一种预置),
它一变就得改代码、发版、所有宿主重来 —— 而"怎么写"恰恰是最常改的那一样。
代码里只留**一组名字**(`ReportPreset`),因为名字是用户能点的把手,也是数据的形状。

**两个出口,一份维护**:装了技能目录的宿主读 `skill/styles.md`;
只认协议、没有技能目录的宿主走 `get_guide(step="styles")` ——
那份说明是 `include_str!` 进二进制的**同一个文件**(与 `ui/*.html` 同一道工序),
所以两边不可能各说各话。有一条测试盯着:代码里每个预设名与中文标题,
`skill/styles.md` 里都得有对应的一节。

`build_report` 的 `style` 必填,四项:

| 槽 | 形状 | 为什么是这个形状 |
|----|------|------------------|
| `preset` | 闭集合:`quick` 快扫版 / `teaching` 教学版 / `story` 故事版 / `review` 元组版 / `exec` 汇报版 / `custom` 自定义 | **它决定"怎么填"**(条数、骨架、详略、证据密度);换风格 = 照另一种轮廓重写一遍 |
| `granularity` | 闭集合:`brief` / `standard` / `detailed` | 这一版实到的粒度 —— 预置给默认值,用户点名就改;它**同时决定条数与篇幅** |
| `tone` | **自由文本**:大白话 / 诙谐 / 讲故事 / 行业腔…… | 语气穷举不了(下周还会有新说法),列不全就别列 —— 但**必须写出来** |
| `notes` | 可选:给谁看、要不要例子、要不要结论先行 | 用户交代了就写 |

> **工具在这一栏上不做判断**(哪种轮廓对他更好,不关工具的事),只保证:
> **填了、不是空的**,而且**`preset` 是那六个名字之一**。
> 空着是最常见的糊弄法 —— 字段在、内容是空白,交付时照样说不清"这份是按什么做的"。
> (乱码字符在这一栏上也**只标不拦** —— 同 §8 那张表下面那条注。)

它落在数据里,所以**三个地方同一个来源**(`ReportStyle::describe`):
页面标题栏的小标签(hover 看补充要求)、`report.md` 的头一行、工具返回里的 `style` ——
交付时模型照着最后那个说一句「这版是教学版;要换成快扫版说一声」。

> **兼容**:`preset` 这一栏是中途加的,所以数据里是 `Option` + `skip_serializing_if`
> (`style` 本身也是)—— 这一栏加进来之前落的报告照样读得动、页面照样渲染,
> 只是小标签上少一个轮廓名。**新报告一律要有**(工具侧必填,`check_style` 兜底),
> 与 `state.bin` 那条同一个道理:**别让加一栏把已有项目全废掉**。

三条口径值得单独说:

- **讲者那侧不经过调用方**(2026-09-27 改;从前是"照抄 `quote` 让工具搜段号")——
  段号不给就按锚点时刻**就近取**(那一刻他讲的就是那几段),给了就按给的。
  理由见 §6.1 那条注:机械的活留给工具,别让模型当打字机。
  落盘的 `TopicSource::Speaker` 仍然读得动(旧报告照样渲染),新报告不再写。
- **每条知识点的凭据由工具补默认**:讲者原话按时刻挂上;"哪张图说明了这条"仍由调用方挑
  (图是离散采样,最近的那张未必在讲这件事),外部来源也由调用方给(只有它知道查到了什么)。
- **看不清的数字分两条路走**([260926-17](../devlog/2026-09.md)):结论**不靠它** → 不写
  (写了就是编);结论**靠它** → **连不确定一起写出来**(「约 3.12(这个版本号画面看不清,待核验)」)
  并挂一条 `verify`(核什么、去哪儿核)。**略过它等于悄悄削弱结论** ——
  读的人看不出少了什么,而这类数字恰恰是结论的支柱。页面上标题栏标着总数、
  每条浮层里逐条列出,交付时也要报这个数。
- **`t` 必给**(锚点),`shots` / `segments` 是关联,**空数组合法** —— "这条不挂图"是确定的状态,
  不是未知(所以空集合写空数组,不写 null)。
- **粒度:一条 = 一处值得单独讲的**。视频里逐个讲的案例 / 步骤 / 样本,**每个各占一条** ——
  各有各的锚点、各有各的画面证据。六张 图表图挤成一张表塞进一条,时间轴上就点不到某一个案例,
  面板里也翻不到"这个案例讲了什么"([260926-13](../devlog/2026-09.md) 实测)。
  这条口径写在 P5 模板正文里,**不做机械校验**:该不该合是内容的判断,
  数一数表格有几行不叫判断(与 §7 同一条:**识别与判断归 agent**)。

> **一处已知的账**:**已还**(2026-09-26)—— 见下面 §8.1.2,重渲染前会复核一遍。

#### 8.1.2 锚点复核:材料变过之后,报告引的东西还在不在

报告数据的锚点是**引用**(截图 id / 段号 / 照抄的话),材料后来变了(校准改了转录、
图重抽了、视频换了)它们不会自动失效。所以**重渲染之前复核一遍**
(`vidbrief_ops::report::stale_anchors`),判据与落盘时**逐条对齐**:图在清单里、
段在转录里、引的话**逐字落在某一段之内**(跨段不算 —— 与 §8.1 第一条同一个道理)。

**只报不拦** —— 这是它与 `build_report` 那条路的区别:

| 路 | 对不上时 |
|----|----------|
| `build_report`(落数据) | **退回**,不许落盘(引的图 / 段 / 链接都得当场对得上) |
| 重渲染(`ui --view report` / `render_existing`) | **照渲染,把过期的列出来** |

为什么重渲染**不拦**:页面恰恰是发现"材料变过"的窗口(段芯片本来就会把找不到的段显灰),
拦下来连看都看不到。但**不能不说** —— 读者照着页面上的一句"讲者原话"回去核、
转录里却没有这句,他就不知道该信谁了。所以三个地方都要出现:**页面标题栏的红标签**
(悬停逐条列)、**CLI 打印的那一段**、**工具返回里的 `stale_anchors`**。
修法是重出一份(`build_report` 整份替换)。

## 9. 可视化:工具生成的 HTML 视图

### 9.1 形态与"弹出 UI"

- MCP 工具 `render_timeline(project_id, open_browser?)` → 生成 HTML,**并顺带启动本地查看服务 + 自动打开默认浏览器**(即"弹出 UI")。`render_calibration_table` 同形态(§9.3)。
- 这是每一步的"图形化检查界面"。
- **本地查看服务是什么**:一个绑在 `127.0.0.1` 的极简 HTTP 静态服务,把项目目录当站点发布(`http://127.0.0.1:<port>/<项目 id>/…`),由工具按需拉起。**(已实现,见 `vidbrief-viz::server`)**
  - **为什么需要**:浏览器直接 `file://` 打开 HTML 时,`<video>` 常因跨域/安全限制无法加载本地视频,"拖时间轴→视频回跳"就会失效;走 `http://127.0.0.1` 后,视图/图片/视频同源,`<video>` 的 seek/播放正常。
  - **必须支持 Range 请求**:没有 `206 Partial Content` + `Accept-Ranges: bytes`,浏览器不会来 seek。
  - **附带好处**:多轮迭代时页面可自动刷新(`Cache-Control: no-store` 已经这么做了)。
  - **与控制通道的关系**:MCP 走 stdio 做 agent↔工具的控制;本地服务只负责"给人看",两者互不冲突。
  - **端口分配(避免冲突)**:服务默认绑 `127.0.0.1:0`,由**操作系统自动分配空闲端口**,不可能撞车;**每个 MCP 进程内只起一个长驻服务**(多项目靠**挂载表**路由,不是每次渲染都新起);进程退出时 OS 自动释放端口。若用户显式指定固定端口且被占用,则自动 +1 重试。
  - **安全**:这是唯一会把磁盘内容发出去的地方,路径要过两道关 —— 先由 `RelPath` 校验 URL 段(拒 `..`/`.`/反斜杠/盘符),再 `canonicalize` 确认仍在挂载根之内(挡符号链接指向外面)。
  - **多会话**:stdio 是"1 会话 1 进程",各会话各起自己的服务、各拿自己的端口,互不冲突;并发写同一项目另见 §4.7。
  - **服务独立成进程,而且给"关掉"一个正门**(2026-09-26,清账四):从前服务是**工具进程里的一条线程**,
    于是"关掉页面" = 杀掉工具自己 —— 而它可能就是 agent 的会话进程(实测踩过)。
    现在 MCP 会话第一次要视图时 spawn 一份 `vidbrief serve`(独立进程):
    - **不连坐**:`vidbrief serve --stop [项目]` 或页面上的关闭都只关服务自己;
    - **不留孤儿**:spawn 时给一条 stdin 管道当心跳(`--watch-stdin`),会话进程一走,
      服务读到 EOF 自己收工;
    - **发现路径**:每个在跑的服务把 `{pid, port, mounts}` 登记在
      `<临时目录>/vidbrief-view/<pid>.json`(**不进项目目录**),`--stop` 靠它找;
    - **控制面**(`POST /@mount` / `POST /@shutdown` / `GET /@status`):挂载表在服务进程手里,
      调用方通过它动态挂项目 —— 挂载不再是"调用者内存里的一张表";
    - 前台 `vidbrief ui`(那个进程本来就只为服务活着)仍是进程内线程,行为不变。
- agent 也可只引用 HTML 路径;在支持内嵌预览的环境里直接展示,不启服务。

## 10. 技术选型与模块划分

### 10.1 语言(统一 Rust,可外挂)

- **核心与 MCP 服务:统一 Rust**。抽帧/差帧是计算与数据流密集;已有可用实现;单二进制分发;MCP 服务与计算同进程。
- **可外挂**:某环节在 Rust 里成本过高时,允许以**子进程**外挂(Python/Node),工具内部 `Command` 调用。外挂须:输入输出走文件/STDIN-STDOUT,无状态,可单测。
- **绝不引入模型 SDK**:工具不调外部模型,故无需任何 LLM/视觉 SDK 与密钥管理。

### 10.2 MCP 协议实现(已定:stdio + 弹出 UI)

- **传输:MCP stdio JSON-RPC**(agent 本地拉起)。**协议层与具体 agent 无关。**
- **可视化交互**:渲染视图的工具在返回 HTML 路径的同时,可**启动本地查看服务并自动打开默认浏览器**(弹出 UI,见 §9.1)。stdio 只做控制,本地服务只负责展示。
- **实现:官方 Rust SDK [`rmcp`](https://github.com/modelcontextprotocol/rust-sdk) 3.1**,已落地(M3)。
  开工前先验证过它在本机**离线可编**(只加依赖、不写代码,`cargo build -p vidbrief-mcp --offline` 25 秒通过),
  再读源码确认 3.x 的形态:`#[tool_router]` / `#[tool_handler]` / `#[prompt]` / `#[prompt_handler]`
  宏、`Parameters<T>` 提取参数、`ToolRouter: Add`(所以工具可以**分组声明再相加**)。
  workspace 的 `rust-version` 因此提到 **1.88**。
- 同时暴露:
  - **Tools**:动作与服务(§11)
  - **Resources**:只读项目文件,URI 形如 `vidbrief://project/<id>/<项目根相对路径>`
  - **Prompts**:内置校准/总结/报告的提示模板(§10.4),降低接入门槛

> ⛔ **stdio 上有一条不能破的规矩:stdout 是协议通道。**
> 任何 `println!`、进度条、调试输出掉进去,客户端就会收到一段不是 JSON-RPC 的字节流,整个会话当场坏掉。
> 所以:**库层(`vidbrief-ops` 往下)根本不打印**,诊断一律走 stderr。
> 端到端测试逐行解析 stdout,这条规矩是被机器守着的,不靠人记。

### 10.3 模块划分

```

├── crates/
│   ├── vidbrief-core/     # 差帧、密集区、抽帧(重写;旧实现已不在本仓库)
│   ├── vidbrief-asr/      # 调 whisper-cli,解析 srt → transcript.json
│   ├── vidbrief-project/  # 项目目录 + 数据结构 + 写锁(契约层叶子)
│   ├── vidbrief-viz/      # 时间线/对照表/报告 HTML 渲染(含视频回跳 + 前端脚本)
│   ├── vidbrief-report/   # MD → HTML 图表化模板
│   ├── vidbrief-ops/      # **动作层**:一步的编排与项目上的读写,CLI 与 MCP 共用
│   ├── vidbrief-mcp/      # MCP 服务:供材料 + 存结论 + 算法动作 + 提示模板
│   └── vidbrief-cli/      # 独立命令行(脱离 agent 也能测/用)

├── docs/

```

> 注意:没有 "vision" 模块——识别由 agent 完成,工具侧无对应代码。

**依赖方向**(只能从上往下):

```
project  ←  core  ←  asr          project  ←  viz          project  ←  report(→ viz)
                    └──────────────┬──────────────┘
                                ops  →  {project, core, asr, viz}
                             ┌────┴────┐
                            cli  →   mcp        ← cli 还会拉起 mcp(`vidbrief mcp` 子命令)
```

> 实测修正:上面那条 `cli → mcp` 是**存在**的 —— `vidbrief mcp` 就是把进程交给
> `serve_stdio`。所以两者不是完全"平等互不依赖":CLI 是宿主,MCP 是它拉起来的一个子命令。
>
> 另外 `vidbrief-cli` 曾经多声明了 `asr` / `viz` 两条**从来没用过**的边(`core` 只在测试里用)——
> Cargo 不会为这种边报警。已拆掉([260925-22](./devlog/2026-09.md))。

`vidbrief-ops` 是 M3 加的**动作层**。判据很直接:
**把这一层删掉,CLI 和 MCP 就得各写一份一模一样的流程**(建项目 = 探测 + 搬运 + 落盘;
步 1 = 视觉 + 转录 + 标记完成 + 渲染)。而它们写的是同一批 JSON —— 两份流程迟早分家。

| 层 | 有什么 | 没有什么 |
|----|--------|---------|
| 契约 `vidbrief-project` | 文件格式、目录、写锁 | 不知道"一步"是什么 |
| 能力 `-core` / `-asr` / `-viz` / `-report` | 单个算法或渲染 | **不跨 crate 编排** |
| 动作 `vidbrief-ops` | "建项目"、"跑步 1"、取材料、存结论 | 不打印、不解析参数、不认识 JSON-RPC |
| 入口 `-cli` / `-mcp` | 参数 / JSON-RPC,把结果说给人或 agent 听 | 不含任何流程判断 |

### 10.4 MCP 提示模板(由本工具提供,内容自定)

> **同一份文本还有一个工具出口**(§11 G 组 `get_guide`)。M5 真 agent 联调发现:
> MCP 的 prompts 是**可选能力**,宿主可以不实现 —— 实测手上的宿主就没实现,
> 四个模板一个都到不了 agent。工具是必选能力,所以 `get_guide(step)` 给同一份说明;
> 文本只在 `crates/vidbrief-mcp/src/prompts.rs` 里维护一处,有测试逐字比对两个出口。
>
> **放出来的前提:模板里提到的每个工具都必须已经存在。**
> 模板是**接口契约** —— 写着"调用 `record_shot_check`",那个工具就必须在工具表里,
> 否则 agent 照着做会拿到 "method not found",然后开始怀疑整个服务。
> 所以按里程碑逐个放开,不做"先把文本写上、工具以后补"的事:
>
> | 模板 | 依赖 | 状态 |
> |------|------|------|
> | P1 `calibrate_shots` | list_shots / get_shot / record_shot_check / render_timeline | ✅ M3 |
> | P2 `fix_transcript` | apply_corrections / render_calibration_table | ✅ M4 |
> | P3 `find_missing_shots` | find_supplement_candidates / extract_shot | ✅ M3 |
> | P4 `summarize_video` | get_transcript / list_regions / list_shots / get_shot / search_transcript / request_shot / write_summary / write_note | ✅ M5 实战打磨 |
> | P5 `build_report` | build_report / get_transcript / list_shots / write_summary | ✅ M6 |
>
> 没放出来的能力**照样能用** —— agent 直接调那些工具就行,只是暂时没有现成的话术。
> `vidbrief-mcp/src/prompts.rs` 里有测试钉住这条规矩(查"每个模板引用的工具都存在"
> 与"未就绪的模板确实没注册")。

**P1 `calibrate_shots`** —— 校准截图
```
你是视频图文校准助手。请对项目中的每张关键截图完成图文匹配与音画同步检查:
1. 调用 list_shots 获取截图清单;对每张调用 get_shot 获取图像与同期转录。
2. 亲自查看图像,并严格对照同期转录:转录明确说的信息(对象/规格/方向)必须服从,
   画面独有的信息(形态/标注线/数值)如实读出并标注"从画面推断"。
3. 若转录与画面矛盾,写入 issues。
4. 用 record_shot_check 逐张存回结论,**每条都带一句照抄的转录原文当凭据**(`evidence_quote`);不要臆测,不确定就标 low confidence / "画面无法确认"。
5. 完成后调用 render_timeline 刷新视图。
```

**P2 `fix_transcript`** —— 转录纠错
```
你是中文金融/技术视频的转录校对员。
逐句检查转录,只修正明确的识别错误(同音错字、专有名词、术语)。纠错依据优先级:
1) 关键帧画面上的文字(最可靠,截图常直接写着正确写法);
2) 上下文语义;
3) 术语表(可能为空;为空时忽略此项):{glossary}
遵守:
- 不改语序、不润色、不改写意思;
- 数字/单位/时间除非明显识别错,否则保留;
- 无把握的句子保留原文并标注 uncertain,不得臆造。
用 apply_corrections 逐条写回(附 reason);完成后调用 render_calibration_table。
```

**P3 `find_missing_shots`** —— 补图
```
调用 find_supplement_candidates 取回候选补图请求(语音提到指代对象但附近无截图)。
逐条判断是否确实需要补图;需要则调用 extract_shot(t, reason)。
完成后 render_timeline 刷新。
```

**P4 `summarize_video`** —— 总结(M5 按联调实测打磨过)
```
你要为这个视频产出一份图文总结:
1. 先建整体结构:list_regions 看画面在哪几段变化密集,list_shots 看有哪些截图、
   各落在什么时刻;转录(get_transcript)通读,太长就按 start/end 分段。
   差帧图原始点(get_change_curve)不必读 —— 它的结论已经在密集区里了。
   通读时把讲者明确给出的**步骤、框架、清单**记下来(流程、「两种方式/四个方面」
   这类分点、列出的清单)—— 那是他特意讲的,总结里要写全;只有闲聊和过渡句可以略。
   实测(M5 内容质检):漏掉的多半是这些**框架**,而它们是视频里信息密度最高的部分。
2. 对每个关键段,用 get_shot 把图拿到眼前看,和同期转录互相对照再下结论。
   get_shot 返回里带着校准阶段存下的旧结论 —— 可以参考,但要自己看过图再引用,不要照抄。
3. 缺画面时先 search_transcript 定位,再 request_shot(t, reason) 补看。
   搜不到时换个词形再试(英文原名 / 中文说法各试一次)。
   **补来的图也要记一条结论**(record_shot_check)—— 不然写总结时门会拦。
4. **一段一段交**(write_summary,一次一段):每段给 t(哪一刻)、title(一句话)、
   md(正文);**视频里逐个讲的逐个成段**(六个案例 = 六段);最后单独交一条**总述**
   (不带 t,进面板开头)。改名 = 再交一次同名的那段。
   正文里:**画面上的文字与数字照抄下来**——看不清就不写那个数,别给一个「差不多」的。
   实测(M5 两轮):不要求照抄时,模型会把 3.12.1 写成 3.21.1、把画面里没有的
   3.12 写成像是读来的数 —— **结构对、数字错**,读的人分不出哪个是抄的。
   看不清但结论靠它的数:连不确定一起写出来,并挂进那一段的 verify。
5. 需要时先写 notes/ 笔记。已有旧稿时先读旧稿再改(用户是在它之上提意见的)。
6. 写完停下来呈现给用户,等他说改哪儿 —— 不要自己接着写报告。
```

**P5 `build_report`** —— 报告(与 `get_guide(step="build_report")` 同一份文本)
```
把步 3 写下的那些段摆成**能对着视频看**的一页 —— **这个工具不用你交内容**:
每条(标题、正文、圆点位置)就是步 3 交过的段;那一刻的转录与画面由工具就近挂上。
1. 先看手上有什么:已有 04_report/report.json 时先读它(用户是在它之上提意见的),
   里面的 style 是这一轮的口味默认值。**段不够或某处讲得不对 → 回步 3 改**
   (write_summary 同名再交一次那段),这里没有重写内容的入口。
2. **先把风格定下来**(`style`,必填,按用户的话填,别自己默认一个):先取
   `get_guide(step="styles")` —— 五种预置风格(快扫 / 教学 / 故事 / 元组 / 汇报)各自怎么填:
   条数怎么按视频长度换算、每条按什么骨架写、给谁看、要不要挂图。挑一种写成 preset;
   granularity 是这一版的粒度(brief / standard / detailed,**同时决定条数与篇幅**);
   tone 是语气(自由文本);notes 放还有的交代。用户没交代就照那张表挑(拿不准用教学版),
   并**在交付时说清这一版是按什么做的**。
3. **定锚点**:通读转录与截图清单,挑出值得单独讲的那几处(一个概念的界定、一次图表的切换、
   一个案例怎么展开),每条给一个时刻(落在视频长度之内)。**视频里逐个讲的,报告里逐个成条**:
   一个个案例/步骤/样本各占一条(它被讲到的那一刻就是锚点,它自己的画面就是证据)——
   合成一张表塞进一条,读的人在时间轴上点不到、在面板里翻不到。条数与篇幅按上面定的档位,
   两头都不许:不堆空标题,也别把几条并成一条。
4. 每条写给「一边看视频一边读」的人(说法按 tone):title 一句话;body 是**完整解析**(浮层里
   显示的就是它,只给标题等于没写);不要写「见上文」这类回指(读的人是跳着看的);shots 放真正
   说明了这条的截图(面板里出图,不给就是没图);segments 放关联段号(**可以不给**,
   不给就按锚点时刻就近取);**画面上的文字与数字照抄**。
5. **讲者那侧不用抄**:他说了什么,工具按锚点就近从转录里取(段号与原文都是工具的事)。
   只有**外部补充**要你给:`external` + 大意 + 能点开的链接(材料没说清的术语/对象/事件才联网补,查不到别编)。
6. 一次 build_report 落数据并出页面,返回的 url 给用户;重做就是再调一次(整份替换)。
7. **写完停下来**问用户要改哪儿,顺带说一句这一版是按什么做的(返回里的 style)。
   没有总结、或总结被绕过工具改过,门会挡住 —— 先落总结,别绕。
```

> **P5 直到 M6 才放出来**([260926-10](../devlog/2026-09.md)):模板是接口契约 ——
> 里面写「调用 build_report」,那个工具就必须存在。工具的入参、门的规矩、数据校验
> 都定下来之后,正文才写得出"要给什么、会被什么挡住"。

### 10.5 命令行(便于不接 agent 时自测)

```bash
vidbrief init <video> [-n id] [-t title] [-p dir]   # 建项目(已实现)
vidbrief preprocess <project> [options]             # 步 1:差帧图/密集区/截图/转录(已实现)
vidbrief status <project> [--verify]                # 状态 + 健康检查(已实现)
vidbrief upgrade <project> [--fresh]                # 对齐到当前版本 / 重起一份状态(已实现,§4.10)
vidbrief approve <project> [-n note]                # 记下"这一步用户看过了"(已实现)
vidbrief correct <project> --json <文件|->          # 转录结论(apply_corrections 的命令行版)
vidbrief shot-check <project> --json <文件|->       # 看图结论(record_shot_check)
vidbrief supplements <project> --json <文件|->      # 处置补图候选(disposition_supplements)
vidbrief summary <project> --md <文件|->            # 写总结(过校准的门)
vidbrief report <project> --json <文件|-> [--format both|html|md] [--open]
                                                    # 出报告:数据 + 页面 + 导出(过步 3→4 的门)
vidbrief ui <project> [--no-open] [--view X]        # 视图 + 本地服务(X: timeline/calibrate/report)
vidbrief mcp        [--stdio]                       # 启动 MCP 服务(已实现)
vidbrief help                                       # 用法
```

> **每个写动作都有一条命令行的路**(devlog [260925-34]):走同一套 `ops` 代码、
> 同一把锁、同一个门 —— 不是另一条捷径。第五轮实测的教训是 MCP 会断
> (agent 把它自己一起关掉了),而当时**四个写动作一个命令都没有**,
> 它手上再没有任何能写项目的入口,只能拿宿主给的文件工具直接改文件。

> CLI 从 M3 起**只剩"解析参数 + 打印"** —— 它写的是**派生视图**,不是材料,
> 所以 `ui` 不取写锁:两个会话同时渲染也不会有坏结果,
> 而"另一个会话正开着项目"不该让查看也变成不可能。

`ui` 会渲染 `01_preprocess/timeline.html`、把项目目录挂到本地服务上、打开默认浏览器。
**服务是必须的**:浏览器用 `file://` 打开时对本地媒体有跨域限制,时间轴点了不跳。

`preprocess` 的选项:`-f/--fps`(采样帧率,默认 1.0)、`-w/--width`(参与打分的缩小宽度,
默认 480)、`--no-transcribe`、`--no-shots`、`--run-id <ID>`(内部契约:MCP 起作业时
给这一趟起名,好让等它的人认得出「就是这一趟」)。**一次作业做完步 1 的全部产出**,
产出里多一份 `01_preprocess/run.json`(**运行记录**,§5.4 —— 谁在跑、跑到第几步、
跑完的交代或失败原因);
源视频没有音轨时转录自动跳过(不是错误);whisper 用不了时**不标记步 1 完成并以非零退出**
(材料保留,重跑即可)—— "我知道我在跳过"必须由用户显式说(`--no-transcribe`)。

`status` 的 `<project>` 两种写法都认:项目目录本身,或 `projects/` 下的项目名。
`--verify` 会重算源视频 sha256 与记录比对(要读一遍视频,几百 MB 要几秒),
用来发现"源文件被**就地改写**" —— 硬链接与软链接都会跟着变,而链接关系看起来毫无异常。

**有硬伤时 `status` 以非零退出码结束**,方便脚本与 agent 判断。

`init` 的行为:校验视频 → 定项目 id(`-n` 显式指定 → `-p` 目录名的净化结果 → 视频文件名净化;
纯中文名净化不出来就要求 `-n`)→ 建目录骨架 → 按硬链接/软链接/复制的顺序把源视频放进 `source/` →
`ffprobe` 探测并写 `source/video.meta.json` → 写 `project.json`。

| 选项 | 含义 |
|------|------|
| `-n, --name <ID>` | 项目 id(ASCII)。默认由文件名净化 |
| `-t, --title <TEXT>` | 人类可读名,可含中文。默认取视频文件名 |
| `-p, --project-dir <DIR>` | **项目目录本身**(直接把项目建在 `<DIR>` 里)。默认 `projects/<id>`;两种写法**都已存在即报错** |

> `-p` 是"项目目录",不是"项目们的父目录"。给了 `-p` 就用它本身,不再套一层。
>
> **位置撞车一律报错,不自动改名 —— 两种写法一样。**
> 这里曾经区分过:显式给 `-p` 撞了就报错,而默认位置 (`projects/<id>`) 因为 id 是工具推出来的,
> 冲突时自动加 `-2` / `-3`。**那个区分是错的**:
>
> 1. **那是命名,命名是人的决定。** `x-2` 是用户会看到、会拿它调工具、会写进报告的标识,
>    工具不该悄悄替他定这个。
> 2. **它对"显式起了名"的情况尤其错。** `-n demo` 明确说了叫 demo,旁边却冒出个 `demo-2`。
> 3. **撞名往往不是"换一个",而是"别建"。** 多半是:这个视频已经建过了、上次建到一半失败了、
>    或者点错了。正确回应都是**看一眼再决定**,不是再造一个出来。
>
> 报错因此分两条去路,让 agent / 用户一次就能选对:
> 那里**是个项目** → "用 `<id>` 就能打开它,**不需要重新建**";那里**是个没建完的目录** →
> 说清两种可能("另一个会话正在建" / "上次失败留下的"),并给出**换个名字另起一个**这条路。
>
> ⛔ **报错文案里不出现"删"。** 读这句话的常常是**模型** —— 你写"删",它就会删,
> 而工具能碰到的目录里装着转录、截图和 agent 的校准结论。该说的永远是**怎么修好**,
> 不是**怎么清掉**。同一条规矩适用于所有 Problem 级文案(见 `health.rs` 里软链接失效那条:
> 它以前劝人"删掉项目用复制重建",那是全仓最危险的一句)。

## 11. MCP 工具清单

**约定**:【供】= 把材料给 agent;【存】= 把 agent 的结论落盘;【算】= 纯算法动作。**没有任何工具调用外部模型 API。**

> **实现进度**:下表**全部已实现**。
> `extract_shot` 与 `request_shot` 是**同一个实现的两个名字**(模板里两种说法都会出现,
> 不必让 agent 记哪一个才对)。
> 唯一退场过的是 `write_report_md` —— "数据为源"([260926-07](./devlog/2026-09.md))之后
> `report.md` 是导出视图,手写它等于给同一份报告立第二处判据;它的活并进了 `build_report`。
>
> **入参的唯一权威是工具自己的 `inputSchema`**(`skill/tools.md` 是它的投影,由测试盯着
> 不许过期);下面这张表是**给人读的概览**,翻一眼知道有哪些工具、大概要什么。
> 2026-09-26 对着活的工具表核过一遍:`get_transcript` / `get_change_curve` 那两个
> `[range]` 早就是 `[start, end]` 了(从 M3 起就漂着),`build_report` 的 `style`
> 也没补进来 —— 这类"手抄的第二份"就是要按上面那条处理。
>
> **参数名不认识就报错**(2026-09-26 起,`deny_unknown_fields`):报错会点名那个字段、
> 列出能认的字段名(例:`unknown field \`range\`, expected one of \`project_id\`, \`start\`, \`end\``)。
> 从前不是这样 —— 拼错的参数**静默失效**,`get_transcript(range=…)` 会老老实实返回
> **全量**材料,agent 拿着它往下做还以为过滤过了。

### B. 步 1 前处理(一件作业,三个入口 —— §5.4)
| 工具 | 类型 | 入参 | 出参 |
|------|------|------|------|
| `preprocess` | 算 | `project_id, [fps, width, transcribe, shots, wait_seconds]` | 跑完了 = 完整交代(差帧图/转录/截图/`timeline.html` 的路径与摘要);还在跑 = 当前进度(不重开) |
| `preprocess_progress` | 供 | `project_id` | 那一趟的状态(running/interrupted/done/failed)+ 走到哪一步 + 抽帧张数 + 已用时 |
| `preprocess_result` | 供 | `project_id` | 跑完的那份交代;没跑完就说「还没好」(不是错误);失败/断了说清原因与重跑的路 |

> 作业跑在**独立进程**里,进度落在 `01_preprocess/run.json`:`preprocess` 只是「起 + 等」,
> 默认等 180 秒(宿主给每次调用 5 分钟上限,留 2 分钟余量),等不够就再调一次接着等。
> **还在跑时不会重开**;跑完了再调才是新的一趟。报 `progressToken` 的客户端还会收到
> `notifications/progress`(五步制,见 §5.4)。

### C. 材料服务(给 agent 看)
| 工具 | 类型 | 入参 | 出参 |
|------|------|------|------|

|------|------|------|------|
| `record_shot_check` | 存 | `project_id, shot_id, {match, audio_visual_sync, type_read, issues, confidence, evidence_quote}` | 更新 `shots.json`。`evidence_quote` 是**照抄**的一句转录原文,工具搜到就记下段号,搜不到拒收(§4.6) |
| `apply_corrections` | 存 | `project_id, [{segment_id, outcome, text?, type?, note?, reason}], [reviewed]` | 更新 `transcript.fixed.json` + `transcript.diff.md`;`outcome` ∈ `corrected`/`kept`/`uncertain`;`reviewed` 是**审过、没问题**的段 id —— 不报等于没审 |
| `write_note` | 存 | `project_id, path, md, [mode], [count_round]` | 写 `02_calibrate/` 与 `03_summary/` 下的 `.md`(交叉印证、校准日志、笔记)。**有专属工具的文件写不了**:`summary.md` 归 `write_summary`、`transcript.diff.md` 归 `apply_corrections` |
| `approve` | 存 | `project_id, [note]` | 用户说"这些我知道,就这样过"时记下来,并快照当时的计数与逐条内容摘要 —— 放行**"要用户拍板"那一批**(§6.1.1、§4.2.1)。**不是门的开关**:没核验的它照样拦 |
| `write_summary` | 存 | `project_id, md` | 落盘 `summary.md`;**先过 `review.calibrate` 那道门**;顺带记下它的内容底账(§6.1.2) |

### E. 算法动作
| 工具 | 类型 | 入参 | 出参 |
|------|------|------|------|
| `find_supplement_candidates` | 算 | `project_id, [window], [rebuild]` | 补图请求清单。`rebuild` 只给"上一份读不动"用 —— **读得动、且上面还有结论时一律拦下**(它会把已有的处置全丢掉;不带 `rebuild` 就会按段号把旧结论合回来) |
| `extract_shot` / `request_shot` | 算 | `project_id, t, reason` | 新 shot_id |
| `update_shot` | 算 | `project_id, shot_id, action(keep/drop/retime), [t]`(`retime` 要给 `t`) | 更新结果 |
| `build_report` | 存 + 算 | `project_id, style{preset, granularity, tone, [notes]}, [format(both/html/md)], [open_browser], [self_contained]` | 落 `04_report/report.json`(**先过步 3→4 的门**,§6.1.2;数据校验见 §8.1),再渲染 `report.html` / `report.md`,并起本地服务。**内容从步 3 的分段来**(`03_summary/sections.json`):一条 = 一个有锚点的段,那一刻的转录段与画面由工具就近挂(`derived_segments` 报条数);`warnings` 是自由正文里的乱码(只报不拦),`stale_anchors` 是重渲染时材料变过的痕迹 |

> `build_report` 为什么既是"存"又是"算":步 4 是**原子产出** —— 一次调用把数据落了、
> 页面出了。分成两个工具,中间那一半状态对谁都没用;重做就是再调一次(整份替换)。
> 它**取写锁**(写材料、动进度),起服务那半与两个视图同一道工序(§9.1)。

| `render_timeline` | 算 | `project_id, open_browser?` | `html_path, url` |
| `render_calibration_table` | 算 | `project_id, open_browser?` | `html_path, url`(对照表内容见 §9.3) |

### G. 说明书(不属于 A–F)
| 工具 | 类型 | 入参 | 出参 |
|------|------|------|------|
| `get_guide` | 供 | `project_id, [step]` | 该步的操作说明(**纯文本**,与提示模板同一份);`step` 不给 = 目录 |

> **为什么有这一组**(M5 真 agent 联调):MCP 的 **prompts 是可选能力** —— 宿主可以不实现。
> 实测手上的宿主就没实现 `prompts/list`:四个提示模板一个都到不了 agent,
> 它只能照着 `instructions` 里那几行自己摸索。**工具是必选能力**,
> 所以同一份说明再开一个工具出口 —— 文本只有一处(`crates/vidbrief-mcp/src/prompts.rs`

## 14. 关键决策(已定稿)

| # | 决策 | 说明 |
|---|------|------|
| 1 | **MCP 传输:stdio** | agent 本地拉起;渲染视图时**可弹出 UI**(启本地查看服务 + 打开浏览器)。实现用官方 Rust SDK `rmcp` 3.1(§10.2)。 |
| 2 | **术语表:默认关闭、可选** | 纠错优先依据"画面文字 + 上下文";用户需要时可补一份领域词表。 |
| 3 | **报告 HTML:相对路径 assets** | 图片默认引用素材(相对路径),避免 base64 单文件膨胀;**单文件分享**是可选的 `self_contained=true`(图内嵌,视频不内嵌,§8 ⑤)。 |
| 4 | **视频回跳:本地查看服务** | 绑 `127.0.0.1:0`(OS 自动分配空闲端口)的极简 HTTP 静态服务,保证 `<video>` 可加载可 seek;与 stdio 控制通道分离;**独立成进程**(MCP 会话 spawn 它,关它不连坐;随会话退出而收工,`serve --stop` 是正门),多会话 = 多进程 = 各端口(§4.7、§9.1)。 |
| 5 | **写锁用 OS 文件锁,锁文件是空哨兵** | 不探 pid:崩溃时 OS 自动释放,而 pid 会被复用。**不往锁文件里写东西** —— 写了就会被 Windows 的强制锁挡得恰恰在需要时读不到(§4.7)。 |
| 6 | **动作层独立成 crate(`vidbrief-ops`)** | CLI 与 MCP 是两个**平等入口**,共用同一套流程;不让任何一个入口依赖另一个(§10.3)。 |
| 7 | **提示模板按"引用的工具已就绪"放开** | 模板是接口契约,不写指向不存在工具的说明(§10.4)。 |

> 至此无遗留待定项,可进入 M0 / M1。

## 16. 风险

| 风险 | 等级 | 缓解 |
|------|------|------|
| 接入的 agent 不具多模态能力 | 高 | 明确前置要求;步 1 仍可用,步 2/3 需看图能力 |
| agent 读图误判(对象/规格) | 中 | 提示模板强制图文联合 + 区分"转录明确/画面推断";对话中人工裁决 |
| ASR 术语错误累积 | 中 | 提示模板 P2 + diff 对照人工确认 |
| 密集区阈值不适配不同视频类型 | 中 | 阈值由曲线统计量自适应 + 视图可视化调参重跑 |
| agent 在步 2/3 发散、成本失控 | 中 | 工具粒度可控 + 补图/检索预算 + 轨迹落盘可审 |
| 多会话并发编辑同一项目互相覆盖 | 中 | 项目写锁 + 原子写 + 修订号(§4.7) |
| 浏览器加载本地视频受限 | 低 | 默认走本地查看服务(§9.1) |
| 视图在长视频下渲染卡顿 | 低 | 时间线窗口化渲染、缩略图懒加载 |
| 报告 HTML 体积膨胀 | 低 | 默认相对路径 assets;自包含模式显式可选 |
| Rust MCP SDK 尚不成熟 | 低 | 抽象传输层;必要时直接实现 tools 的 JSON-RPC |
